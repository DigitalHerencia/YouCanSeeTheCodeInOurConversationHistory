# Make Every Ontology/Recipe Demonstrate a Distinct UI Capability

**Priority:** P2  
**Phase:** Showroom  
**Task status:** Backlog

## Outcome

Ensure each domain surface visibly exercises a different reusable presentation and behavior pattern instead of feeling like the same table with renamed nouns.

## Why This Exists

The master and backlog associate CRM, projects, support, invoicing, social, portal, admin, and AI with different archetypes.

## Execution Checklist

- [ ] Map each supported recipe/domain to its intended primary UI archetypes.
- [ ] CRM: pipeline/kanban, contact directory, account detail, analytics.
- [ ] Projects: backlog, kanban, timeline/Gantt, my tasks.
- [ ] Support: inbox, split-pane ticket workspace, chat/history, SLA analytics.
- [ ] Marketing: campaign studio, audience management, attribution/analytics.
- [ ] Invoicing: invoice builder/detail, directory, expense flow, financial status.
- [ ] Social: calendar, composer, media library, publishing states.
- [ ] AI: generation workspace, prompt/config controls, usage/history.
- [ ] Portal: shared dashboard, document vault, billing/status.
- [ ] Admin: record inspection, bulk operations, audit log.
- [ ] Use showroom seed data to ensure each archetype appears populated and intentional.

## Acceptance Criteria

- [ ] Each supported recipe has a visibly distinct flagship interaction/presentation pattern.
- [ ] No recipe is merely a renamed copy of another route.
- [ ] Reusable blocks are demonstrated through real domain surfaces.
