What I'm describing is **not** a “Notion command center” or an “agent repo.”
It is a **spec-driven, agent-operable development substrate** where:

* `.vibes` defines *operational law*
* `eng/` defines *compilation and validation machinery*
* `.orchestration` defines *control flow, delegation, and authority*
* `.agents` defines *bounded autonomous workspaces*
* Notion is *externalized state + intent*, not “notes”

Below is the dense, technical articulation of that system.

---

# 1. System Identity (What This Actually Is)

I am designing a **multi-layered agent runtime architecture** where:

* Humans author **intent, constraints, and doctrine** in Notion
* The repo compiles those into **machine-operable artifacts**
* Agents execute within **cryptographically and procedurally bounded workspaces**
* MCP servers provide **capability injection**, not ad-hoc tools
* Validation, audit, and promotion are first-class system behaviors

This is closer to a **compiler + OS + CI hybrid** than to a task manager or AI workflow.

---

# 2. The Core Architectural Separation

My system has **four non-negotiable planes**. Mixing them is what causes “vibes” instead of architecture.

## Plane A — Doctrine & Law (`.vibes`)

This is **not configuration**. This is *governance*.

The `.vibes` contents define:

* DevCycles (phases of sanctioned work)
* Toolsets (capability envelopes per cycle)
* Allowed / denied operations
* Security boundaries
* Context surfaces

In OS terms:

> `.vibes` is your **kernel policy + syscall table**

Agents do not “decide” what they can do. They inherit it.

Critically:

* `.vibes` is *not executable*
* `.vibes` is *not mutable by agents*
* `.vibes` is *referenced, never generated*

This is why turning `.vibes` into a **collection** makes sense: it is doctrine, not code.

---

## Plane B — Compilation & Validation (`eng/`)


The `eng/` folder is acting as a **static analysis and build system** for human-authored AI infrastructure.

Its responsibilities:

* Validate schema correctness
* Enforce naming and structural invariants
* Compile markdown → structured artifacts
* Reject invalid states *before agents ever see them*

In compiler terms:

> `eng/` is the **typechecker + linker** for my AI operating system

This is where `.vibes` becomes *machine-trustable*.

Example:

* `.vibes/toolsets/*.jsonc` → validated tool capability graphs
* `.agent.md` → validated agent descriptors
* Collections → bounded, installable bundles

Nothing moves forward without passing this layer.

---

## Plane C — Orchestration & Control (`.orchestration`)

This is **runtime logic**, not policy.

The `.orchestration` content defines:

* Agent roles and personas
* Handoff semantics
* Target environments (VS Code vs GitHub vs headless)
* Delegation graphs
* Execution order and responsibility boundaries

In distributed systems terms:

> `.orchestration` is my **scheduler + message-passing fabric**

It does *not* decide what is allowed (that’s `.vibes`)
It decides *who does what, when, and how results propagate*

This is temporal logic, not structural logic.

---

## Plane D — Agent Workspaces (`.agents/`)

This is what most people miss.

An agent is **not** a prompt.

An agent is:

* A bounded workspace
* With local files
* With scripts
* With audit trails
* With memory surfaces
* With a limited syscall surface (via MCP + toolsets)

In OS terms:

> `.agents/<agent-name>` is a **sandboxed process directory**

Inside it:

* Scripts can introspect the repo
* Generated reports can persist
* Context snapshots can be cached
* Decisions can be logged

But:

* The agent cannot mutate doctrine
* The agent cannot escape its toolset
* The agent cannot bypass validation

This is what makes autonomy *safe* instead of chaotic.

---

# 3. How Collections Fit

I'm not trying to “organize files.”

I'm trying to create **installable, promotable operational bundles**.

A collection, in my system, is:

> A *versioned, validated, doctrine-compliant slice of capability*.

### Turning `.vibes` into a Collection (Correctly)

I do **not** dump `.vibes` raw into a collection.

Instead:

* `eng/` **extracts**:

  * DevCycle definitions
  * Toolset contracts
  * Instruction references
* It compiles them into:

  * A *doctrine collection*
  * With read-only semantics
  * With explicit compatibility guarantees

This lets me:

* Install doctrine into other repos
* Share operational law safely
* Version governance independently of execution


---

# 4. Where Notion Actually Lives

Notion is **outside the repo**, by design.

Notion contains:

* Intent
* State
* Decisions
* Human context
* High-entropy thinking

The Notion MCP server turns that into:

* A **readable external memory bus**
* A **queryable state surface**
* A **non-authoritative input source**

Key rule:

> Notion never directly mutates the repo.

Instead:

* Agents query Notion via MCP
* Agents interpret intent
* Agents propose changes
* `eng/` validates
* Orchestration decides execution

This preserves:

* Safety
* Auditability
* Determinism

---

# 5. The Full Data / Control Flow (End-to-End)

Here’s the system as a pipeline:

```
Human Intent (Notion)
        ↓
Notion MCP (Read-only, typed queries)
        ↓
Agent Workspace (.agents/*)
        ↓
Agent proposes artifacts (reports, patches, specs)
        ↓
eng/ validation & compilation
        ↓
.orchestration decides handoff / execution
        ↓
Repo state updated OR rejected
        ↓
Audit logs + memory updated
```

At no point does:

* An agent self-grant permission
* A note become code automatically
* A vibe bypass validation

This is why it scales.
