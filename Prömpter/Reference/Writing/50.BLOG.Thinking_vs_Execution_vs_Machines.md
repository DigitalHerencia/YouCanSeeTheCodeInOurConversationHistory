---

# 1. The core distinction (don’t overcomplicate it)

| Format             | Optimized for     | Reality                       |
| ------------------ | ----------------- | ----------------------------- |
| **Markdown (.md)** | Humans            | Loose, expressive, contextual |
| **YAML (.yaml)**   | Humans → Machines | Structured but readable       |
| **JSON (.json)**   | Machines          | Strict, unambiguous, fast     |

That’s it. Everything else is just people pretending it’s deeper.

---

# 2. Mental model (this is the one you keep)

```text
Thinking → Markdown
Planning → YAML
Execution → JSON
```

If you follow that alone, you’ll avoid 90% of chaos.

---

# 3. Markdown — where you think and explain

### Use it for:

- PRDs

- architecture docs (like the monster you dropped earlier)

- dev journals

- prompts

- agent definitions (`.agent.md`, `.prompt.md`)

### Why:

- flexible

- supports narrative

- can embed code blocks (YAML/JSON inside it)

### Example

```md
# Feature: Catalog Manager

We need:

- CRUD wraps
- image uploads
- publish controls

## Constraints

- no Prisma in UI
- actions handle mutations
```

👉 Markdown is **for brains**, not systems.

---

# 4. YAML — where you define structured intent

### Use it for:

- specs

- configs

- agent inputs/outputs

- pipelines

- anything “semi-structured”

### Why:

- readable by humans

- parseable by machines

- supports hierarchy without noise

### Example (your world)

```yaml
feature: catalog-wrap-editor
route: /catalog/manage/[wrapId]/edit

inputs:
    - wrapId

fetchers:
    - getWrapById

actions:
    - updateWrap

components:
    - wrap-form-shell
    - wrap-image-uploader
```

👉 YAML is your **contract layer**

---

# 5. JSON — where things actually run

### Use it for:

- API payloads

- tool calls

- LLM structured outputs

- anything strict + programmatic

### Why:

- no ambiguity

- strict typing

- universally supported

### Example

```json
{
    "feature": "catalog-wrap-editor",
    "status": "complete",
    "filesCreated": ["features/catalog/manage/edit-wrap-page-feature.tsx"]
}
```

👉 JSON is your **execution layer**

---

# 6. Machine-readable vs human-readable (the real answer)

### Human-readable = forgiving

- Markdown → very forgiving

- YAML → somewhat forgiving

### Machine-readable = strict

- JSON → zero forgiveness

---

## Why JSON wins for machines:

- explicit keys

- no indentation ambiguity

- no comments

- deterministic parsing

---

## Why YAML wins for humans:

- less noise

- easier scanning

- supports comments

---

## Why Markdown wins for thinking:

- no schema required

- narrative + structure

- can evolve without breaking anything

---

# 7. How a senior dev actually uses all three (this is the important part)

They **don’t pick one**.

They **layer them**.

---

## Example pipeline (your exact use case)

### Step 1 — Thinking (Markdown)

```md
# Wrap Editor

We need edit flow with:

- form
- image manager
- publish controls
```

---

### Step 2 — Structured spec (YAML)

```yaml
feature: wrap-editor

routes:
    - /catalog/manage/[wrapId]/edit

actions:
    - updateWrap

components:
    - wrap-form
    - wrap-image-manager
```

---

### Step 3 — Agent execution (JSON)

```json
{
    "task": "generate-feature",
    "feature": "wrap-editor",
    "constraints": ["no-prisma-in-ui"]
}
```

# 8. Rules you should actually follow

## Rule 1 — Don’t use Markdown for structured data

If you’re parsing it → wrong format

---

## Rule 2 — Don’t use JSON for humans

If you’re reading it → you’ll hate yourself

---

## Rule 3 — YAML is your bridge

Use it when:

- humans write it

- machines read it

---

## Rule 4 — Keep boundaries clean

Don’t mix:

```md
- some text
- random JSON blob
- YAML kinda but not really
```

That’s how systems rot.

# 10. The real mistake people make (don’t do this)

They try to use ONE format for everything.

That leads to:

- unreadable configs

- unparseable docs

- broken automation

---

# Final blunt truth

- Markdown = thinking

- YAML = planning

- JSON = execution

If you respect that separation, your system scales.

If you ignore it, you end up with a pile of half-structured nonsense that no human or machine actually understands.

And then you’ll blame the tools instead of the structure.
