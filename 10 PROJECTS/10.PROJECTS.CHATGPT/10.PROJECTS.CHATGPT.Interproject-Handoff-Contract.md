# ChatGPT Interproject Handoff Contract

## Purpose

This file is the durable coordination contract between the user's specialized ChatGPT Projects.

The user may tell any Project to check this contract and the shared message board. That instruction is the transport mechanism between otherwise separate Project conversations. The user should not have to reconstruct or summarize the underlying work when a durable handoff already exists here.

Shared message board:

`10 PROJECTS/10.PROJECTS.CHATGPT/10.PROJECTS.CHATGPT.Message-Board.md`

## Operating Model

The user remains the authority for genuine product, architecture, business, and priority decisions.

For the current Codependent Coding workflow:

- **Chief of Staff** owns operational project state: Project Manager task state, sequencing, dependencies, active/waiting/blocked/completed state, delegation state, and next-action visibility.
- **Vibes** owns knowledge integrity: authoritative architecture/knowledge reconciliation, contradiction and drift detection, propagation of established decisions, and bounded Codex preparation.
- **Codex** performs bounded engineering implementation from the authoritative assignment it receives.
- **Trust Issues** independently verifies whether the requested outcome actually exists and satisfies the stated contract.
- **Execution** handles concrete execution that does not belong to a more specialized lane.
- **The user** resolves genuine decisions and may explicitly change any prior decision or delegation boundary.

## Project Manager Boundary

For Codependent Coding, the Obsidian Project Manager project is the operational source of truth for work state.

Other Projects may report PM signals but must not independently redefine task status, percentage, sequencing, dependencies, due dates, or completion state.

Chief of Staff translates verified handoff signals into Project Manager state.

A claim such as `implemented` is not equivalent to `verified` or `done`.

## Knowledge Boundary

Vibes determines the controlling knowledge package for Codependent Coding implementation work by reconciling the active architecture, terminology, Simples, Ontologies, Source Mirror evidence, repository reality, corrections, and generation semantics.

Existing implementation does not automatically redefine architecture. A newer note does not automatically supersede an older authority. Genuine unresolved decisions return to the user.

## Standard Handoff Payload

Every durable cross-project handoff should use this payload:

```text
PROJECT:
WORK PACKAGE:
FROM:
TO:
DATE:

STATE:
ready | blocked | needs-decision | implemented | verified | failed | informational

WHAT CHANGED / WHAT WAS LEARNED:

AUTHORITATIVE EVIDENCE:

UNRESOLVED ITEMS:

REQUESTED NEXT ACTION:
```

`TO: ALL` may be used for a message relevant to every Project.

## State Semantics

- `ready` — the sender has completed its prerequisite work and is handing the package forward.
- `blocked` — work cannot proceed until a named dependency or condition is resolved.
- `needs-decision` — a genuine user decision is required; agents must not silently choose.
- `implemented` — execution has been performed but independent verification has not necessarily passed.
- `verified` — Trust Issues or another explicitly authorized verifier has independently confirmed the required outcome.
- `failed` — verification or execution failed against the stated contract.
- `informational` — durable context with no immediate state transition requested.

## Routing Rules

For the Codependent Coding workflow, the normal route is:

`User decision -> Vibes knowledge package -> Codex implementation -> Trust Issues verification -> Chief of Staff PM update -> next cycle`

Exceptions are allowed when the work genuinely belongs elsewhere. For example, Vibes may directly perform knowledge reconciliation, and Execution may perform miscellaneous concrete work.

If verification exposes an implementation defect, route it back to Codex or the relevant executor.

If verification exposes unclear or contradictory canon, route it to Vibes first.

If a genuine unresolved decision remains after reconciliation, route it to the user.

## Message Board Protocol

The message board is a mailbox and handoff log, not a second project-management system.

When the user tells a Project to **check the message board**, that Project should:

1. Read this contract if it has not already adopted it or if the contract changed.
2. Read the newest relevant message addressed to that Project or `ALL`.
3. Perform only the requested next action within its role boundary.
4. Produce a new handoff using the standard payload when its work reaches a durable transition.
5. Ask the user to have Chief of Staff or the named next Project check the message board when another Project must act.

Projects should prefer durable evidence links, file paths, commit SHAs, verification results, and exact task identifiers over conversational recollection.

## Bootstrap Message for Other ChatGPT Projects

The user may paste the following once into each participating Project:

> Shared cross-project coordination lives in my DevNotes repository under `10 PROJECTS/10.PROJECTS.CHATGPT/`. Read `10.PROJECTS.CHATGPT.Interproject-Handoff-Contract.md` and use `10.PROJECTS.CHATGPT.Message-Board.md` as the durable handoff mailbox. When I tell you to "check the message board," read the newest message addressed to your Project or `ALL`, follow the contract and your existing Project role, and produce a standard handoff for the next Project when needed. Do not independently change Codependent Coding Project Manager state unless you are Chief of Staff. I remain the authority for genuine decisions.

## Anti-Bureaucracy Rule

This mechanism exists to reduce the user's coordination burden.

Do not create additional cross-project contracts, dashboards, status systems, message buses, or duplicate PM records unless the user explicitly requests them or the existing two-file mechanism demonstrably cannot represent the needed handoff.
