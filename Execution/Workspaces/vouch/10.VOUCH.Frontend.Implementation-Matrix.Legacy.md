# Vouch Frontend Implementation Matrix

## Purpose

This document converts the Vouch page taxonomy into a frontend implementation inventory.

It defines which feature orchestrations, shared components, domain components, UI primitives, route shells, and provider/layout boundaries are required for the MVP interface.

This is not a design brainstorm. This is an implementation control document.

Every frontend file should serve one of these surfaces. If a component does not map to a page category, interaction surface, or reusable primitive need, it should be removed, renamed, or folded into the correct layer.

---

## Implementation Chain

```txt
Page taxonomy
-> feature orchestration inventory
-> component purpose inventory
-> UI primitive standardization
-> route shell normalization
-> layout/provider normalization
```

The order matters.

Pages define the required features.

Features justify components.

Components reveal which primitives need standardization.

Routes and layouts become thin shells around the approved structure.

---

## Layer Rules

### Route Files

Location:

```txt
app/**/page.tsx
```

Route files may:

```txt
define metadata
receive params/searchParams
wrap dynamic content in Suspense
render one page-level feature
render static shared components for static pages
redirect when required
```

Route files must not:

```txt
query Prisma
call Stripe
call Clerk business logic beyond route/session handoff
shape protected DTOs
perform domain mutations
own form logic
own provider reconciliation
own settlement logic
```

---

### Feature Orchestrations

Location:

```txt
features/*
```

Feature files own page-level composition.

Server features may:

```txt
call fetchers
receive DTOs
compose page sections
perform role-aware branching from DTO state
hand data to client features
```

Client features may:

```txt
own React Hook Form wiring
own drawer/dialog state
own transition/pending state
call server actions from forms/buttons
render action result state
```

Feature files must not become reusable UI libraries.

---

### Shared Components

Location:

```txt
components/shared/*
```

Shared components render reusable page structure.

Examples:

```txt
PageHero
SectionIntro
CalloutPanel
ContentSectionList
ProcessPanel
MetricGrid
CardGrid
Surface
```

Shared components must not:

```txt
fetch protected data
call server actions directly
own domain truth
import Prisma
import Stripe
import Clerk server APIs
```

---

### Domain Components

Location:

```txt
components/vouches/*
components/dashboard/*
components/forms/*
```

Domain components render Vouch-specific UI from DTOs and content modules.

They may display state.

They must not create state truth.

---

### UI Primitives

Location:

```txt
components/ui/*
```

UI primitives are low-level reusable building blocks.

They should be brutalist, square, high-contrast, accessible, mobile-first, and consistent.

They must not contain Vouch business language or domain rules.

# Matrix 1: Page Categories to Routes

| Category | Route(s) | Route Type | Owned by Vouch? | Notes |
|---|---|---:|---:|---|
| Funnel Page | `/` | Public | Yes | Conversion landing page |
| Product Definition / Pricing | `/pricing` | Public | Yes | Pricing label, product explanation function |
| Dense Informational / Legal | `/faq`, `/legal/terms`, `/legal/privacy` | Public | Yes | FAQ/legal/reference rendering |
| Auth Pages | `/sign-in`, `/sign-up` | Auth | Yes, Clerk-backed | Custom shell/forms, Clerk auth underneath |
| Dashboard Index | `/dashboard` | Tenant | Yes | Index of Vouch cards |
| Protocol Action | `/vouches/new` | Tenant | Yes | Create one new Vouch |
| Vouch Detail | `/vouches/[vouchId]` | Tenant | Yes | Operational center for one Vouch |
| Provider Return | `/checkout/success` | Public/provider return | Yes | Return surface, not payment truth |
| Connect | External Stripe | Provider | No | Stripe-hosted Connect onboarding/dashboard |
| Payment | External Stripe | Provider | No | Stripe-hosted saved payment method flow |
| User Account | Clerk surface | Provider/component | No | Clerk account/profile surface |
| Protocol Drawers | Embedded surface | Interaction | Yes | Not routes |

# Matrix 4: UI Primitive Standardization

## Required UI Primitives

| Primitive | Purpose | Vouch Optimization |
|---|---|---|
| `Button` | All action triggers | square, uppercase, high-contrast, loading state |
| `Input` | Form fields | dense, high-contrast, clear error state |
| `Textarea` | Rare; avoid unless needed | likely not needed for MVP |
| `Checkbox` | Agreement/disclaimer gates | explicit label/body support |
| `Form` | RHF/Zod form presentation | field/error consistency |
| `Drawer` | Default high-consequence surface | mobile-first bottom drawer |
| `Dialog` | Interruptive confirmation only | reserve for exceptional use |
| `AlertDialog` | destructive/emergency action | archive/destructive only if needed |
| `Badge` | Status label | text-first, not color-only |
| `Separator` | Dense layout rhythm | brutalist borders |
| `Skeleton` | Loading shape | page-specific but primitive-backed |
| `Toast` | Action feedback | safe messages only |
| `Tooltip` | Context hints | optional, not required |

---

## Primitive Design Requirements

All primitives should support:

```txt
rounded-none
bordered surfaces
black/neutral foundation
high contrast
uppercase labels where appropriate
restrained blue action color
status text not color alone
mobile-first sizing
keyboard accessibility
visible focus states
loading/disabled states
```

Do not create decorative primitives that do not serve the product surface.

# Matrix 6: Provider Normalization

## Root Providers

Canonical root provider stack:

```txt
ClerkProvider
ThemeProvider if used
TooltipProvider if used globally
ToastProvider if used globally
```

Provider rules:

```txt
No provider soup inside page files.
No Stripe provider globally unless Stripe Elements are truly rendered internally.
No domain state providers unless necessary.
No client-only provider for server-owned truth.
```

---

## Stripe Provider Rule

Stripe-hosted flows are external surfaces.

Do not add Stripe Elements providers unless the app intentionally renders Stripe Elements internally.

For MVP, preferred model:

```txt
Stripe hosted Checkout / payment method / Connect flows
```

Therefore Stripe provider context should generally not be needed in React page trees.

---

## Clerk Provider Rule

Clerk provider belongs at root.

Clerk user/account components may be used for account surface if needed.

Clerk components must not become Vouch settings pages.

# Final Frontend Invariant

Every frontend artifact must answer one question:

```txt
What approved Vouch surface does this serve?
```

If the answer is unclear, the artifact is suspect.

If the artifact creates a new product behavior, it is probably wrong.

If the artifact only looks cool, it must either become purposeful or leave.

Vouch’s frontend should be brutal, narrow, and operational.

The product is the Vouch object.

The interface exists to create it, understand it, list it, inspect it, and act on it.
