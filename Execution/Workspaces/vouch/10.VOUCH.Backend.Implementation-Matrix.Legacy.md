# Vouch Backend Implementation Matrix

## Purpose

This document converts the Vouch server-side domain taxonomy into a backend implementation inventory.

It defines the canonical domains, services, operations, supporting modules, persistence boundaries, provider integrations, schemas, DTOs, tests, and validation gates required for the Vouch MVP.

This is not a brainstorm.

This is an implementation control document.

Every backend artifact should serve one of the approved domains, services, operations, integrations, transactions, validation contracts, or transport contracts defined here.

---

## Implementation Chain

```txt
Source of truth
-> domain taxonomy
-> service inventory
-> operation inventory
-> supporting module inventory
-> tests and validation
```

The backend is organized around business capability, not pages.

Frontend base unit:

```txt
page surface
```

Backend base unit:

```txt
domain capability
```

Frontend orchestration unit:

```txt
feature
```

Backend orchestration unit:

```txt

```

```txt

```

```txt

```

## Layer Vocabulary

### Domain

A domain is a business capability Vouch must support.

Examples:

```txt

Readiness
Vouch Lifecycle
Pricing
Payment Coordination
Confirmation
Settlement
Webhook Reconciliation

```

### Service

A service coordinates related backend operations for a domain.

Services are not React components.

Services are not route handlers.

Services are server-side orchestration modules.

### Operation

An operation is one named executable behavior.

Examples:

```txt
getDashboardData
createDraftVouch
commitVouch

confirmPresence
resolveSettlement

```

```txt

DTOs

mappers

integrations

```

## Global Backend Rules

Every protected fetcher must follow:

```txt
authenticate
-> authorize
-> minimal select
-> DTO mapping
-> cache policy
-> transport-safe return
```

Every server action must follow:

```txt
authenticate
-> authorize
-> Zod validate
-> transaction and/or provider operation
-> audit event
-> revalidate
-> typed result or redirect
```

Every webhook handler must follow:

```txt
read raw body
-> verify provider signature
-> classify event
-> record provider event id
-> idempotently process valid transitions
-> return provider-compatible response
```

The Clerk webhook handler must remain explicitly modeled as a Clerk webhook handler.

Internal app writes use server actions.

External provider events use webhook handlers.

Protected reads use fetchers.

Atomic persistence uses transactions.

Provider calls use integration modules.

Transport contracts use DTOs.

Input validation uses Zod schemas.

# Matrix 1: Domain Inventory

| Domain | Purpose | Primary Services | Critical Rule |
|---|---|---|---|
| Identity | Map Clerk identity to local Vouch account state | Auth service, Clerk webhook service | Clerk owns auth truth; Vouch owns domain account truth |
| Authorization | Decide whether a user may read or mutate a resource | Authz service | Authz does not mutate |
| Readiness | Determine whether user can create, accept, pay, receive, or confirm | Readiness service | Readiness is embedded gating, not a standalone setup surface |
| Vouch Lifecycle | Manage Vouch state progression | Vouch service | Lifecycle state is deterministic |
| Pricing | Calculate fee and immutable pricing snapshots | Pricing service | Fee math is server-owned |
| Invitations | Create and resolve invite links | Invitation service | Invite links do not create marketplace behavior |
| Payment Coordination | Coordinate Stripe-backed payment setup and authorization | Payment service, Stripe service | Stripe owns payment truth |
| Connect / Payout | Coordinate Stripe Connect onboarding/readiness | Connect service | Provider-hosted, not internal settings page |
| Confirmation | Validate bilateral presence confirmation | Confirmation service | No one-sided release |
| Settlement | Resolve capture/non-capture/refund from workflow + provider truth | Settlement service | Retrieve provider state before acting |
| Webhooks | Reconcile provider events idempotently | Stripe webhook service, Clerk webhook service | Duplicate events are harmless |
| Audit | Record deterministic system history | Audit service | Audit is not dispute evidence |
| Recovery | Retry technical inconsistencies without discretion | Recovery service | Recovery cannot rewrite business truth |
| DTO Mapping | Convert persistence/provider state into transport-safe UI state | Mapper services | No raw provider/Prisma leakage |
| Configuration | Validate env and provider config | Config service | No secret leakage |

# Final Backend Invariant

Every backend artifact must answer one question:

```txt
What Vouch domain capability does this serve?
```

If the answer is unclear, the artifact is suspect.

If the artifact creates discretionary outcomes, it is wrong.

If the artifact exposes manual settlement, it is forbidden.

If the artifact is provider-facing, it must verify, normalize, idempotently reconcile, and return safely.

If the artifact is user-facing, it must authenticate, authorize, validate, mutate atomically, audit, and revalidate.

Vouch backend architecture exists to enforce one rule:

```txt
both parties confirm within the confirmation window
-> provider truth permits capture
-> funds release

otherwise
-> refund, void, expiration, or non-capture according to state
```

Stripe owns payment truth.

Clerk owns authentication truth.

Vouch owns workflow truth.

The Clerk webhook handler remains a webhook handler.
