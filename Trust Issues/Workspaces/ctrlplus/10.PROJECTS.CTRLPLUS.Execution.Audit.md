\# What you actually built



CtrlPlus is effectively:



> A single-business vehicle-wrap operating system with catalog management, AI-assisted visualization, scheduling and capacity management, customer records, billing, Stripe Checkout, platform administration, audit trails, Cloudinary assets, Clerk identity, and capability-based global authorization.



The repository describes itself both as “tenant-scoped” and “org-scoped RBAC,” but your canonical data-model document correctly calls the operating model \*\*single-store\*\*.

```text
&#x20;   ↓

&#x20;   ↓

```



Your pure `hasCapability()` and `requireCapability()` policy functions are separated from session resolution, while guards compose authentication and capability checks for particular use cases.



That is \*\*actual RBAC\*\*, albeit:



\* global rather than tenant-specific,

\* hardcoded rather than database-configurable,

\* and supplemented by ownership checks.



Your session pipeline also has a coherent identity-resolution order:



```text

Clerk identity

&#x20; → explicit environment bootstrap override

&#x20; → persisted global role

&#x20; → customer default

```



For your experience level, that is very good architectural decomposition.



\## 2. Scheduling shows actual concurrency awareness



This surprised me.



Reservation and booking creation:



\* validate store-time constraints,

\* count overlapping bookings,

\* check customer conflicts,

\* perform the operation in a PostgreSQL `Serializable` transaction,

\* create the booking, reservation, and audit record atomically.



That means you—or an executing agent operating under your direction—understood that:



```text

then insert booking

```



is unsafe unless the check and insert are protected from concurrent transactions.



That is not beginner thinking.



Your transaction helper also centralizes the capacity calculation and overlapping-active-booking definition rather than scattering it across UI code.

\# Now let’s talk shit



\## P0: The Stripe webhook can become permanently catatonic



Your webhook claim logic creates an event with:



```text

status = processing

lastAttemptedAt = now

```



If processing crashes:



1\. The event stays `processing`.

2\. Stripe retries it.

3\. The unique ID prevents another insert.

4\. The claim function sees `processing`.

5\. It returns `"processing"`.

6\. The payment handler returns a duplicate/pending response.

7\. Your route returns HTTP 200.

8\. Stripe stops retrying.

9\. The event remains stuck forever.



Only rows with `status = failed` can be reclaimed. There is no processing lease, stale-lock cutoff, or administrative retry transition for abandoned `processing` events.



Vouch had a \*\*broken stale lease\*\*.



CtrlPlus looked at that and said:



> “What if we simply had no lease at all?”



\### Fix



Add:



```text

lockedAt

lockToken

attemptCount

nextAttemptAt

```



Then atomically claim when:



```text

status ∈ received, failed



OR



status = processing

AND lockedAt < staleCutoff

```



Never acknowledge a currently processing event as successfully handled unless you know another worker owns a valid live lease.

\## P0: `checkout.session.completed` is treated as “money definitely settled”



Your processor handles only:



```text

checkout.session.completed

```



It retrieves the PaymentIntent—but only to extract the payment method. It does not validate:



\* `session.payment\_status`,

\* `paymentIntent.status`,

\* session currency,

\* canonical invoice amount,

\* the invoice version embedded when Checkout was created.



It then creates a `Payment` with `status: "succeeded"` and marks the invoice `paid`.



Stripe explicitly distinguishes completed Checkout from settled delayed payments. Delayed methods can require `checkout.session.async\_payment\_succeeded` or `async\_payment\_failed`, and Stripe’s fulfillment guidance says to inspect payment status and make fulfillment idempotent. (\[Stripe Docs]\[1])



\### Why this matters



Because you do not restrict Checkout to card-only methods, Stripe can potentially enable eligible delayed methods through its dynamic payment-method configuration.



A customer could complete authorization while the payment is still processing, and CtrlPlus would label the invoice paid.



\### Fix



The canonical handler should:



```text

retrieve Checkout Session from Stripe

retrieve/expand PaymentIntent

verify session belongs to invoice

verify currency

verify expected total

verify invoice is payable

verify payment status



if succeeded:

&#x20;   settle invoice



if processing/unpaid:

&#x20;   record pending payment



handle async\_payment\_succeeded:

&#x20;   settle invoice



handle async\_payment\_failed:

&#x20;   mark payment failed

```

\## P0: Old Checkout Sessions can pay stale invoice state



You wisely put `invoice.updatedAt` into:



\* the Stripe idempotency key,

\* and Checkout metadata.



But the webhook does not compare that metadata against the current invoice.



So this can happen:



1\. Invoice total is $1,000.

2\. Checkout Session A is created.

3\. Owner applies a $300 credit.

4\. Invoice is now $700.

5\. Session A remains open.

6\. Customer pays $1,000 using the stale session.

7\. Webhook takes `session.amount\_total`.

8\. Invoice becomes paid.



Or the reverse: an old lower-value Checkout remains valid after increasing the invoice.



The handler currently accepts `session.amount\_total ?? invoice.totalAmount` and does not compare the two.



\### Fix



A payment attempt should be a first-class record:



```text

InvoicePaymentAttempt

&#x20; invoiceId

&#x20; checkoutSessionId

&#x20; paymentIntentId

&#x20; expectedAmount

&#x20; currency

&#x20; invoiceVersion

&#x20; status

```



Mutating an issued invoice should invalidate or expire its prior unpaid Checkout Sessions—or produce a new immutable invoice revision.

\## P0/P1: Stripe customers can duplicate under concurrency



When an invoice lacks a Stripe customer ID, `createCheckoutSession()` calls:



```text

stripe.customers.create(...)

```



without a stable idempotency key. Only afterward does it upsert the customer ID locally.



Two concurrent requests can both see no customer, create two Stripe Customers, and race to persist whichever ID writes last.



\### Fix



Use:



```text

idempotencyKey = customer:{clerkUserId}:create

```



And model the creation operation locally so the intended customer ID relationship is recoverable.

\## P1: Side effects after payment settlement are not reliably recoverable



After the payment and invoice transaction commits, the webhook performs:



\* payment-settings synchronization,

\* audit logging,

\* owner email,

\* customer email,

\* and only then marks the webhook processed.



Suppose payment settlement succeeds but email fails:



1\. Payment exists.

2\. Invoice is paid.

3\. Webhook becomes failed.

4\. Stripe retries.

5\. Handler sees the existing payment.

6\. It immediately finalizes the event as processed.

7\. Failed emails and possibly other post-payment work are never retried.



Your payment side effect is idempotent. Your \*\*secondary side effects are not durably tracked\*\*.



\### Fix



Use an outbox:



```text

payment transaction:

&#x20; update payment

&#x20; update invoice

&#x20; create audit event

&#x20; enqueue payment\_received notification jobs

&#x20; mark fulfillment complete



worker:

&#x20; deliver each outbox job idempotently

```



Do not make Stripe’s webhook delivery responsible for the reliability of your email provider.

\# Scheduling: good concurrency, confused clocks



You validate appointment windows using `America/Denver`.



Then your capacity transaction derives:



\* weekday with `getUTCDay()`,



\* slot time through a separate HH:mm conversion.



That creates a plausible mismatch around timezone offsets and day boundaries.



An appointment considered Monday afternoon in the store timezone could be classified using its UTC weekday/time when matching an availability rule.



\### Fix



All scheduling calculations need one explicit temporal model:



```text

stored timestamps       UTC instants

store availability      local wall-clock rules + IANA timezone

comparison              convert instant into store-local date/time

DST behavior            explicitly tested

```



Also, you use serializable transactions correctly but do not appear to retry serialization failures. Under contention, PostgreSQL can abort a transaction even when the code is correct. Add a narrow retry loop for Prisma `P2034`.



That is a production-hardening issue, not an architectural embarrassment.

\# Data modeling: good entities, weak constraints



For two years in, your model is impressive in breadth:



\* catalog entities,

\* many-to-many category mappings,

\* bookings and reservations,

\* immutable booking price/name snapshots,

\* invoices and line items,

\* payment records,

\* provider event ledgers,

\* visualizer uploads and generated previews,

\* audit records,

\* asset metadata and hashes.



The apprenticeship fingerprints are:



\## Stringly typed lifecycle state



Many important states are plain strings with comments describing allowed values:



```text

globalRole

booking.status

invoice.status

payment.status

webhook.status

preview.status

```



The database will happily accept:



```text

status = "paid-ish-but-not-really"

```



Move controlled, durable lifecycles into Prisma enums or PostgreSQL check constraints.



\## External IDs where foreign keys could exist



Bookings and several owner-scoped objects store Clerk user IDs directly rather than relationally connecting to the local `User`.



That can be intentional, but it forfeits database referential integrity and complicates user deletion/reconciliation.



\## Payment semantics are overloaded



During refund creation, the `Payment.stripePaymentIntentId` field receives a Stripe \*\*refund ID\*\*.



That field is no longer semantically a PaymentIntent ID. It is a generic Stripe transaction ID wearing the wrong nametag.



Use a distinct `Refund` model or at least:



```text

providerObjectType

providerObjectId

parentPaymentIntentId

```

\# Uploads through 8 MB Server Action bodies



Your Next config explicitly raises the Server Action body-size limit because catalog assets flow as data URLs.



That is understandable for making the feature work.



It is not the production end state.



Base64/data-URL uploads:



\* add encoding overhead,

\* pass large payloads through your application server,

\* increase memory pressure,

\* couple media upload reliability to Server Action execution.



Use direct signed Cloudinary uploads, then submit the resulting asset identity and metadata to your action.
