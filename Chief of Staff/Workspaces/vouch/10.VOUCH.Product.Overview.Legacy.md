# **vouch.core.md**

_(The Only Document That Actually Matters)_

## 1. Core Thesis

Vouch is a **presence-based payment release system**.

Money is committed before a meeting and only released when both parties confirm physical presence.

Everything else is noise.
If a feature doesn’t support this, it dies.

---

## 2. Problem Statement

Humans are unreliable.

- People cancel last minute
- People don’t show up
- People scam deposits
- People don’t trust each other

Existing tools:

- Payment apps = no conditional release
- Marketplaces = too heavy, too involved
- Cash = zero protection

**Gap:**
No lightweight system enforces _“show up or don’t get paid.”_

---

## 3. Core Mechanism (Non-Negotiable)

A Vouch is a **conditional payment agreement** between two verified adults.

### Lifecycle:

1. Payer commits funds
2. Payee accepts
3. Both parties meet
4. Both confirm presence
5. Funds release

If step 4 fails → refund

That’s the whole company. Don’t get cute.

---

## 4. System Principles

### 4.1 No Trust Assumed

System replaces trust, it doesn’t rely on it.

### 4.2 No Arbitration

You are not a judge.
System outcomes are deterministic.

### 4.3 No Marketplace Layer

No discovery, no profiles, no browsing.

### 4.4 No Social Features

No reviews, no ratings, no messaging system.

### 4.5 Minimal Surface Area

Every added feature increases:

- Legal exposure
- Scam vectors
- Complexity

So… don’t.

---

## 5. Roles

### Payer

- Initiates Vouch
- Commits funds
- Can release funds

### Payee

- Accepts Vouch
- Must show up
- Receives funds

No other roles exist unless you enjoy ruining things.

---

## 6. Trust Model

Trust is created through:

### 6.1 Identity Verification

- Real person
- Age verified (18+)

### 6.2 Financial Commitment

- Money locked = intent signal

### 6.3 Presence Confirmation

- GPS proximity OR dual confirmation

No reviews. No reputations.
This is not Yelp for humans.

---

## 7. Payment Architecture (Critical)

Vouch does NOT hold funds.

- Funds go through Stripe Connect (or equivalent)
- Platform orchestrates state, not money custody
- “Escrow-like,” not legal escrow (important distinction)

If you touch money directly:
→ welcome to regulatory hell

---

## 8. Presence Model

### Primary

- GPS proximity threshold (~1000 ft)

### Secondary (fallback)

- Dual manual confirmation

### Constraints

- Both must confirm
- One-sided confirmation = no release

---

## 9. Time Logic

Each Vouch has:

- Start window
- Expiration window

### Outcomes:

**Both confirm within window**
→ Release funds

**No confirmation**
→ Refund

**Partial confirmation**
→ Refund

No disputes. No appeals. No crying.

---

## 10. Failure Modes

Design for these, or enjoy getting wrecked:

- User never shows
- User shows but doesn’t confirm
- GPS fails
- App not opened
- Payment auth fails

System response must always be:
→ deterministic and predictable

---

## 11. Legal Positioning (Don’t Be Stupid)

Vouch is:

- A coordination tool
- A payment trigger system

Vouch is NOT:

- A marketplace
- A broker
- A facilitator of services

Users:

- Arrange their own interactions
- Accept their own risks

You are infrastructure, not a participant.

---

## 12. UX Philosophy

Interface should feel:

- Serious (money is involved)
- Fast (no friction)
- Clear (no ambiguity)

Avoid:

- Playfulness
- Social fluff
- “Engagement features”

Nobody wants dopamine.
They want their money.

---

## 13. Anti-Features (Things You Will Be Tempted to Add and Must Not)

- Profiles
- Ratings
- Messaging system
- Search / discovery
- “Boosted users”
- AI anything (please, I beg you)

Every one of these moves you closer to:
→ legal risk
→ platform liability
→ death

---

## 14. Expansion Surface (Later, Not Now)

If (and only if) core works:

- Recurring Vouches (subscriptions)
- Group Vouches (multi-party)
- API access (third-party integrations)

Not before product-market fit.
Not because you’re bored.

---

## 15. Success Criteria

You are successful if:

- Users complete Vouches without confusion
- Funds release/refund correctly every time
- No disputes require human intervention

You are failing if:

- Users ask “what happens if…”
- You need customer support
- You add features to “increase engagement”
