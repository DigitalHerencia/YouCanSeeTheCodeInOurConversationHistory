# Codependent Coding Consolidation — Codex Handoff

## Objective

Continue the approved consolidation program using **actual repository state**. Do not jump directly into the Database workbench before the target repository can host it.

The next implementation sequence is:

```text
1. Establish CodependentCoding as the single Next.js application root
2. Preserve/rehome the current Hipster Stack website as that app foundation
3. Preserve only genuine shared/package boundaries
4. Verify the consolidated app builds and runs
5. Then implement the Simple workbench contract
6. Use Database as the first end-to-end workbench slice
```

## Current Repository Reality

### `DigitalHerencia/CodependentCoding`

Current `main` is still the **old knowledge-system repository shape**:

```text
.agents/
.github/
AGENTS.md
MANIFEST.md
README.md
docs/
patterns/
provenance/
```

There is currently no root Next.js `app/` and no root application `package.json` in the inspected repository tree.

Its current `AGENTS.md` explicitly says the repository's product is the written knowledge system. That instruction now conflicts with the approved consolidation direction and must be reconciled as part of the repository transition rather than silently ignored.

### `DigitalHerencia/TheHipsterStack`

This repository currently combines several responsibilities:

```text
repository root
├── apps/web/             # deployed Hipster Stack Next.js website
├── packages/*            # shared/generator implementation
├── tests/
├── scripts/
├── context/
├── docs/
└── root package.json     # publishable hipster-stack CLI package
```

`pnpm-workspace.yaml` currently includes both `apps/*` and `packages/*`.

The root package is the publishable `hipster-stack` CLI package with `bin: dist/cli.mjs`; it is **not** the web application's package definition.

`apps/web/` is already shallow and contains the material that should become the consolidated site's runtime foundation:

```text
app/
components/
features/
lib/
components.json
next.config.ts
package.json
postcss.config.mjs
tsconfig.json
```

The web package currently depends on `@hipster-stack/core` through `workspace:*`.

## Approved Target Topology

The user-approved target is:

```text
CodependentCoding/
├── app/                  # ONE App Router root
├── components/
├── features/
├── lib/
├── public/
├── docs/ or normalized knowledge source as actually required
├── packages/             # ONLY genuine package/distribution boundaries
├── tests/                # only tests justified by actual implementation
├── package.json          # root Next.js application/package manager authority
└── ...root config
```

Hard rules:

- one Next.js application;
- one root `app/`;
- no `src/`;
- no permanent `apps/web` wrapper;
- do not preserve a monorepo shape merely because the old repository had one;
- do not destroy a genuine shared/distribution boundary merely to satisfy aesthetic flattening;
- Maximal Template code remains real source files;
- Docs and Simples ultimately project one knowledge model;
- generator/Constituter work remains later than the current demo/workbench effort.

## Package-Boundary Rule

Do **not** flatten packages mechanically.

`@hipster-stack/core` is currently imported by the web app and participates in generator/configuration behavior. During the initial consolidation, preserve it if removing it would create a second implementation or break a real shared-engine boundary.

After the application is stable, reassess each package:

```text
Needs independent publication/distribution?      → package boundary justified
Shared by web + CLI/generator engine?             → package boundary may be justified
Used only by the root application?                → prefer root app/lib ownership
Exists only because old monorepo did?              → eliminate
```

The CLI itself is secondary in the new direction. Do not let preserving the old root CLI package force the entire new repository to remain organized around the CLI.

## Phase A — Reconcile Repository Governance

Before broad source moves:

- update repository identity from “knowledge system is the product” to **Codependent Coding umbrella product + application**;
- preserve useful doctrine/provenance material as source material;
- do not delete old material until winning replacements and provenance are established;
- update `AGENTS.md` so an execution agent is not simultaneously told both “this is a docs-only product” and “build the application here.”

The new instruction should preserve the architecture classifier and owner-approval/canonicalization gates, but recognize the repository as executable software.

## Phase B — Establish the Root Next.js App

Use the current `TheHipsterStack/apps/web` implementation as the migration source.

Move/rehome, do not rewrite for sport:

```text
TheHipsterStack/apps/web/app         → CodependentCoding/app
TheHipsterStack/apps/web/components  → CodependentCoding/components
TheHipsterStack/apps/web/features    → CodependentCoding/features
TheHipsterStack/apps/web/lib         → CodependentCoding/lib
TheHipsterStack/apps/web/public      → CodependentCoding/public   # if present in actual checkout
web Next/PostCSS/shadcn/TS config    → root equivalents
```

Preserve the existing design, Docs, Simples/Libraries, and Constituter surfaces long enough to refactor them deliberately.

Do not copy `.next`, `node_modules`, generated caches, deployment output, or local secrets.

## Phase C — Resolve Dependencies Intentionally

The current web app imports `@hipster-stack/core`.

For each such import:

1. identify the actual used contract/function;
2. determine whether it belongs to a genuine shared generator/domain package;
3. preserve the package temporarily when that is the smallest coherent move;
4. do not duplicate the same resolver/model under `lib/` just to remove a workspace import.

The repository should become simpler through resolved ownership, not through copy/paste duplication.

## Phase D — Preserve Public Behavior

Before redesigning anything, prove the migrated site preserves the current routes/surfaces that matter:

- landing/public site;
- Docs;
- Simples/Libraries;
- `/configure` / Constituter;
- existing visual system/assets.

Do not combine migration and visual redesign into one giant diff unless a move mechanically requires it.

## Phase E — Verify the Foundation

Run the repository's real applicable gates after migration.

At minimum for the root web app:

```text
install
format/check as configured
typecheck
lint
next build
```

Run any existing tests/architecture validation that remain applicable after ownership is resolved.

Do not claim success until the new root application actually builds.

### Database is the first slice

The first workbench should consume the real file-level Database/read-path records rather than the old static `libraries.ts` fields.

Initial source set:

```text
lib/db/client.ts
lib/db/tenant.ts
lib/db/provider.ts
lib/db/transactions/tenant-context.tx.ts
prisma/migrations/20260815000000_application_owned_tenancy/migration.sql
prisma.config.ts
types/access.ts
lib/auth/identity.ts
lib/fetchers/projectsFetchers.ts
lib/db/selects/projects.selects.ts
lib/db/dto/projects.dto.ts
```

### First real interactive source consequence

For Projects Fetchers:

```text
Public Showroom
    withTemplateReadTransaction(...)

Hardened Template
    withAuthenticatedTenantTransaction(...)
```

That control changes actual displayed code. It is a **workbench source edition selector**, not a generator security toggle.

## Monaco / Codebase Context Utility

Inspect and reuse the useful Codebase Context Utility ideas rather than importing the old app wholesale.

Actual inspected source:

- `components/file-tree.tsx` already provides useful recursive selected-file explorer mechanics;
- `components/file-system-provider.tsx` owns useful filesystem state/read behavior;
- `components/code-preview.tsx` currently loads selected file content and detects language by extension.

Important correction:

> `CodebaseContextUtility/components/code-preview.tsx` currently renders `<pre><code>`. It does **not** use Monaco.

If Monaco is adopted for the Codependent Coding workbench, introduce it deliberately as a new client-only source-view dependency and keep it read-only by default.

## Stop Conditions

Stop and report rather than improvising when:

- migration exposes an unresolved ownership conflict between CodependentCoding and Hipster Stack source;
- preserving `@hipster-stack/core` requires a package decision that changes the approved product topology;
- a source file contains secrets or generated local state;
- a supposed public/hardened difference is not supported by the knowledge/source material;
- the build cannot be made green without changing unrelated architecture;
- owner canonicalization approval is required for a substantive doctrine choice.

## Definition of Done for the Next Codex Run

The preferred next-run completion target is **not the whole platform**.

A successful bounded run produces:

1. CodependentCoding repository governance updated for the new executable umbrella role;
2. current Hipster Stack website successfully rehomed as the root Next.js application;
3. required shared package boundaries preserved intentionally;
4. existing public/Docs/Simples/Constituter surfaces still present;
5. root application passes the applicable engineering gates;
6. no source repository deleted or destructively rewritten;
7. a clean handoff stating exactly what remains before Database workbench implementation.

If that foundation is completed with substantial token/time remaining, proceed to the Database workbench as a second bounded phase. Do not bury a failed consolidation under UI work.
