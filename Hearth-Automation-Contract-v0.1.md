# Hearth Automation Contract v0.1

## 1. Human vs machine state

Human state is edited through Meta Bind.
Machine state is generated by workflows and reconciliation.
Computed state is derived from source notes and task state.

Never require a user to edit a computed value because a dashboard needs it.

## 2. Completion

A TaskNotes task is complete when TaskNotes reports the configured done status.
The completion timestamp is written once when the task first enters a done state.
Subsequent refreshes do not rewrite the original completion timestamp.

## 3. Progress

Phase progress:

`completed non-cancelled tasks / total non-cancelled tasks * 100`

Milestone progress:

`completed non-cancelled tasks across its phases / total non-cancelled tasks across its phases * 100`

Project progress:

`completed non-cancelled tasks across its phases / total non-cancelled tasks across its phases * 100`

If the denominator is zero, progress is `0`.

Cancelled tasks do not contribute to either side of the calculation.

## 4. Health

Computed health state follows this precedence:

1. `complete` when the parent is done.
2. `blocked` when a linked active blocker exists.
3. `at-risk` when an active item is overdue or its target end has passed.
4. `on-track` otherwise.

Human-entered `risk` remains a Phase judgment and is not silently overwritten.

## 5. Current milestone and phase

Current milestone = first non-cancelled milestone in explicit project milestone order whose status is not `done` or `cancelled`.

Current phase = first non-cancelled phase inside the current milestone whose status is not `done` or `cancelled`.

If no current phase exists, the project is review-ready for the milestone transition.

## 6. Next action

`next_action` is generated from executable work, not stored as an independent task database.

Selection precedence:

1. active task explicitly marked blocked/resolution-required is excluded;
2. ready/in-progress tasks are preferred over backlog tasks;
3. due today beats later due dates;
4. overdue beats future dates;
5. higher priority beats lower priority;
6. earlier creation order breaks ties.

If no executable task exists, the engine emits the appropriate lifecycle action:

- complete missing required document;
- perform review;
- perform phase review;
- perform milestone review;
- close project;
- or `none`.

## 7. Daily load

Daily Note generation MUST NOT dump the entire backlog.

Default executable task projection is a maximum of three tasks:

- one current-focus task when available;
- then the next two highest-priority executable tasks.

Overdue tasks are shown in a separate warning section and do not consume the three-task focus count.

The user can explicitly expand the task view from the Command Center/Base without changing the source-of-truth task set.

## 8. Yesterday

The daily engine reads the previous working day's completed tasks.

For each completed task it shows:

- task link;
- project/phase context;
- completion date;
- linked produced artifacts;
- linked evidence when present.

A narrative sentence is never invented from task title alone.

## 9. Output provenance

A workflow that creates a document/artifact from a task must immediately write the artifact link to the task's machine provenance field.

Examples:

- New PRD from Task -> task `produced` contains the PRD.
- Evidence from Task -> task `evidence` contains the Evidence note.
- Review from Phase -> phase `review` points to the Review note.
- Code Lab drill evidence -> drill/task `production_evidence` contains the Evidence note.

This provenance is what makes later daily rollups trustworthy.

## 10. Daily generation

The Daily Notes plugin creates/opens the note.
Templater renders the template.
A shared daily engine resolves deterministic context.

The generated regions are:

- `CONTEXT`
- `YESTERDAY`
- `TODAY`
- `DEADLINES`
- `BLOCKERS`
- `CADENCE`
- `RECENT OUTPUTS`
- `ZETTLECASTEN QUEUE`
- `RESOURCE REVIEW`
- `CODE LAB`
- `SYSTEM HEALTH`

User-authored regions are:

- focus choice;
- manual decisions;
- notes;
- meeting discussion;
- reflection;
- shutdown notes.

Only generated regions are replaced by Refresh Daily.

## 11. Cadence generation

Daily creation does NOT create all recurring meetings.

The Daily Note only projects meeting/review items relevant to that date.

Actual meeting notes are created only when:

- the user invokes the specific QuickAdd action;
- the user invokes Generate Today's Cadence; or
- a workflow explicitly creates a review note as part of a lifecycle transition.

## 12. Zettelkasten processing

A Zettelkasten item remains in the workbench while unprocessed.

Processing produces one or more durable outputs in `3.RESOURCES` and writes provenance back to the source item.

The source item then moves to the configured processed/archive state. It is not duplicated indefinitely across both systems.

## 13. Property reconciliation

Reconciliation is idempotent.
Running it twice without source changes produces the same result.

Reconciliation must not overwrite user-controlled fields except when a specified lifecycle transition explicitly requires it.

## 14. Repair behavior

When a relation cannot be determined safely:

- preserve the source;
- create/update a repair-queue entry;
- do not invent a relation;
- do not mark the entity valid merely because it exists.
