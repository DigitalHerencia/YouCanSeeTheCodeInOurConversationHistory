# The BusinessLogic™ Blocks

## Workflow Orchestration Layer Specification

**Status:** Canonical Specification
**Architecture:** The Codependent Coding™ WebApp Architecture
**Technology Stack:** The Hipster Stack™
**Domain Library:** The Maximal Template™
**Configuration System:** The Anthimeria™ Workbench
**Application Definition:** The Virgule™
**Generated Artifact:** The Arrangement™
**Generator / Enforcement:** Loaded Vibes™

---

# 1. Purpose

This specification defines the **BusinessLogic™ Blocks** layer of The Codependent Coding™ WebApp Architecture.

BusinessLogic™ Blocks are implemented as **Workflows**.

A Workflow is:

> **A named reusable workflow that constitutes application logic from existing server operations and helpers.**

The BusinessLogic™ Blocks layer is the canonical reusable application-logic layer beneath Feature Orchestration.

Its responsibility is to give identifiable application behavior a stable, reusable orchestration boundary without replacing, absorbing, duplicating, or obscuring the lower-level server capabilities from which that behavior is constituted.

The governing architecture is:

```text
Domain Ontology™
        ↓
    App Router
    ├── Page Routes
    └── Webhook Handlers
        ↓
    Feature Orchestration
    └── Feature Components
        ├── PureUI Presentation Layer™
        │   └── Component Blocks
        │       └── UI Primitive + Variant
        │           └── Semantic Design Tokens
        │
        └── BusinessLogic Blocks™
            └── Workflows
                ├── Server Operations
                │   ├── Auth / Authz
                │   ├── Actions
                │   └── Fetchers
                │
                ├── Integrations
                │   ├── Stripe
                │   ├── Clerk
                │   └── selected providers
                │
                ├── Utils
                │
                ├── Data Transport
                │   ├── DTO Mappers
                │   ├── Prisma Selects
                │   └── Transactions
                │
                ├── Helpers
                │   ├── Constants
                │   ├── Params
                │   └── Cache
                │
                ├── Types
                ├── Interfaces
                └── Zod Schemas
```

# 2. Governing Definition

## 2.1 BusinessLogic™ Block

A **BusinessLogic™ Block** is a named, reusable unit of application behavior represented by a Workflow.

Within this architecture:

```text
BusinessLogic Block™ = Workflow
```

The terms identify the same architectural unit from two perspectives:

- **BusinessLogic™ Block** describes its role as a reusable behavioral capability.

- **Workflow** describes its implementation as an orchestration of existing capabilities.

A BusinessLogic™ Block is therefore not a new category separate from `lib/workflows/`.

Its canonical implementation boundary is:

```text
lib/workflows/{domain}/*Workflow.ts
```

---

## 2.2 Workflow

A **Workflow** is a named reusable orchestration boundary that constitutes application logic by arranging existing server operations and helpers according to the:

- rules;

- sequencing;

- dependencies;

- conditions;

- decisions;

- invariants;

- failure boundaries;

- authorization requirements;

- persistence requirements;

- provider requirements;

- cache consequences;

- and other behavioral relationships

required to realize one coherent application behavior.

In canonical form:

```text
existing server operations + helpers
                ↓
       behavioral arrangement
                ↓
          BusinessLogic™
              Block
                ↓
             Workflow
                ↓
   reusable application behavior
```

The Workflow owns the **behavioral constitution**.

It does not take ownership of the underlying capabilities.

---

# 3. Constituted, Not Composable

BusinessLogic™ Blocks follow the doctrine:

> **Constituted, Not Composable.**

A Workflow is not a physical bundle into which its dependencies are copied or moved.

Its constituent operations remain independently valid architecture-owned capabilities.

For example:

```text
fetcher
action
authorization policy
transaction
provider operation
cache helper
schema
domain helper
        │
        │ arranged according to
        │ application rules
        ▼
BusinessLogic™ Block
        │
        ▼
named application behavior
```

Removing the Workflow removes that particular arrangement.

It does **not** imply removal of the underlying capabilities.

A fetcher may be shared by several Workflows.

An authorization policy may be shared by several Workflows and Features.

A transaction may support more than one behavior.

An integration operation may participate in several application processes.

A schema may validate inputs used throughout the application.

The Workflow is the stable name for the **relationship among those capabilities when they are acting as one application behavior**.

---

# 4. Layer Responsibility

The BusinessLogic™ Blocks layer owns:

- reusable application behavior;

- orchestration of multiple server capabilities;

- sequencing;

- conditional execution;

- business-rule coordination;

- cross-operation decision points;

- dependencies between application operations;

- behavioral invariants;

- failure boundaries at the application-process level;

- coordination of persistence and provider effects;

- reusable domain calculations when they require an application process;

- reusable lifecycle transitions;

- coordination of required authorization;

- coordination of required cache lifecycle behavior;

- dependency closure for configurable application behavior.

The BusinessLogic™ Blocks layer does **not** own:

- URL boundaries;

- HTTP request handling;

- page composition;

- rendering;

- UI state;

- presentation;

- persisted-read implementation;

- ordinary CRUD implementation;

- authentication implementation;

- authorization-policy implementation;

- transaction implementation;

- provider mechanics;

- database selects;

- DTO mapping implementation;

- generic utility implementation;

- runtime-schema ownership;

- semantic design tokens.

---

# 5. Architectural Ownership

Underlying capabilities retain their canonical architectural responsibilities.

|Responsibility|Canonical owner|Workflow relationship|
|---|---|---|
|Identity / session establishment|`lib/auth/`|Uses established identity when behavior requires it|
|Authorization|`lib/authz/`|Evaluates existing permissions, policies, and resources|
|Persisted reads|`lib/fetchers/`|Invokes Fetchers to obtain persisted state|
|Ordinary CRUD mutation|`lib/actions/`|Invokes Actions when the behavior requires ordinary mutation|
|Atomic database invariants|`lib/db/transactions/`|Invokes Transactions when several database effects require shared atomicity|
|Prisma projections|`lib/db/selects/`|Uses canonical Selects through their appropriate data-access boundary|
|Data transport|`lib/db/dto/`|Uses DTO Mappers for architecture-approved transport shapes|
|Provider behavior|`lib/integrations/{provider}/`|Invokes provider-owned operations|
|Cache lifecycle|`lib/cache/`|Coordinates required invalidation or cache behavior|
|Constants|`lib/constants/`|Uses canonical domain constants|
|Params / domain utilities|`lib/utils/`|Uses canonical utility and parameter helpers|
|Runtime validation|`schemas/`|Depends on canonical Zod schemas|
|Domain types|`types/`|Uses canonical types|
|Domain interfaces|`types/`|Uses canonical interfaces|

A Workflow MUST NOT reimplement a responsibility merely because it participates in the behavior.

---

# 6. Feature Orchestration Relationship

Features and BusinessLogic™ Blocks are different orchestration boundaries.

## Feature Orchestration

A Feature answers:

> **What application capability must this interface expose?**

A Feature may coordinate:

- presentation;

- BusinessLogic™ Blocks;

- Fetchers;

- Actions;

- Auth;

- Authz;

- application state;

- client boundaries;

- and other application-level capabilities.

## BusinessLogic™ Block

A Workflow answers:

> **What arrangement of server capabilities constitutes the reusable behavior required by this application capability?**

The relationship is:

```text
Route
  ↓
Feature
  │
  ├──────────── PureUI Presentation Layer™
  │                  ↓
  │             Component Blocks
  │                  ↓
  │              UI Primitives
  │
  └──────────── BusinessLogic™ Blocks
                     ↓
                  Workflows
                     ↓
         Server Operations + Helpers
```

A Feature MAY use several Workflows.

A Workflow MAY be reused by several Features.

A Feature MAY directly use a Fetcher or Action when no meaningful reusable Workflow exists.

The architecture does not require Workflow ceremony around trivial operations.

---

# 7. Workflow Eligibility

A new BusinessLogic™ Block exists only when there is a meaningful reusable behavioral constitution.

The classifier is:

```text
REUSABLE ORCHESTRATION OF APPLICATION LOGIC?

Does this behavior arrange multiple server operations,
helpers, rules, conditions, decisions, dependencies,
or effects into a named application behavior?

    YES → BusinessLogic™ Block / Workflow

    NO  → place the capability according to
          its own architectural responsibility
```

Examples that may justify a Workflow include:

```text
advance deal stage
resolve task dependencies
calculate SLA
advance campaign sequence
finalize invoice
publish scheduled post
execute AI generation
approve client deliverable
perform administrative override
```

Examples that ordinarily do not require a Workflow include:

```text
rename a project
change a contact phone number
update a display name
archive a simple record
perform an isolated CRUD mutation
perform an isolated persisted read
```

> **BusinessLogic™ Blocks are first-class logic units, not mandatory ceremony.**

---

# 8. Workflow Constitution

Every canonical Workflow MUST have a machine-resolvable **constitution**.

The constitution identifies the exact existing capabilities required for that Workflow.

Conceptually:

```text
Workflow
├── identity
├── domain
├── purpose
├── feature consumers
├── server operations
│   ├── auth
│   ├── authz
│   ├── actions
│   └── fetchers
├── integrations
├── data transport
│   ├── DTO mappers
│   ├── Prisma selects
│   └── transactions
├── helpers
│   ├── cache
│   ├── constants
│   └── params / utils
├── schemas
├── types
├── interfaces
├── sequencing rules
├── conditions
├── invariants
├── failure boundaries
├── effects
└── dependency closure
```

The constitution describes **relationships**.

It does not duplicate source implementation.

---

# 9. Exact Dependency Mapping Requirement

The normalized ontology inventory defines:

1. the canonical Workflow files;

2. the canonical server-operation and helper inventory available to each domain;

3. provider integrations supported by each domain;

4. routes and Features that use those Workflows.

The normalized ontology inventory does **not yet enumerate an exact dependency subset for every individual Workflow**.

Therefore:

> **No implementation, generator, documentation agent, or architecture agent may invent an exact per-Workflow constituent mapping and present it as canonical merely from filename similarity.**

Instead, every canonical Workflow MUST acquire an explicit constitution manifest that selects its dependencies from the canonical domain inventory defined in this specification.

The resulting relationship is:

```text
canonical domain inventory
          ↓
exact Workflow constitution
          ↓
dependency closure
          ↓
validated BusinessLogic™ Block
```

The exact constitution of:

```text
lib/workflows/crm/advanceDealStageWorkflow.ts
```

for example, may use only the applicable canonical CRM capabilities listed below, but this specification does not falsely assert that every CRM capability is required by that Workflow.

---

# 10. Dependency Closure

A BusinessLogic™ Block exposed through Anthimeria or Loaded Vibes MUST be dependency-resolvable.

```text
Select BusinessLogic™ Block
           ↓
Resolve exact Workflow constitution
           ↓
Resolve required Server Operations
           ↓
Resolve required Auth / Authz
           ↓
Resolve Data Transport requirements
           ↓
Resolve Integrations
           ↓
Resolve Helpers
           ↓
Resolve Types / Interfaces / Schemas
           ↓
Validate shared dependency graph
           ↓
Retain required implementation artifacts
```

A constituent required by multiple Workflows MUST remain shared.

Removing one Workflow MUST NOT remove a constituent still required elsewhere.

---

# 11. Provider and Transaction Boundary

A Workflow may coordinate both database and provider behavior.

It MUST preserve the distinction between them.

```text
Workflow
├── database effects
│     └── transaction where atomicity is required
│
└── network/provider effects
      └── integration operations
```

Provider/network operations MUST remain outside database transactions.

A Workflow MAY determine sequencing between persistence and provider behavior, but it MUST NOT convert a network operation into part of a database transaction.

---

# 12. BusinessLogic™ Blocks Are Not a Service Layer

The BusinessLogic™ Blocks specification does not authorize generic service abstractions.

The following remain prohibited without separate architectural justification:

```text
services/
managers/
processors/
use-cases/
application-services/
domain-services/
business-services/
```

A Workflow MUST NOT become:

- a miscellaneous server-code container;

- a replacement for Actions;

- a replacement for Fetchers;

- a replacement for Transactions;

- a replacement for Auth;

- a replacement for Authz;

- a replacement for Integrations;

- a wrapper around every server function;

- an object containing duplicated copies of dependencies.

---

# 13. Import Direction

The intended dependency direction is:

```text
Feature
   ↓
Workflow
   ↓
architecture-owned server capabilities
```

BusinessLogic™ Blocks MAY depend on:

```text
lib/auth/
lib/authz/
lib/actions/
lib/fetchers/
lib/integrations/
lib/utils/
lib/db/selects/
lib/db/dto/
lib/db/transactions/
lib/cache/
lib/constants/
schemas/
types/
```

BusinessLogic™ Blocks MUST NOT depend upon the presentation hierarchy:

```text
components/templates/
components/blocks/
components/ui/
semantic design token implementation
```

Presentation and BusinessLogic™ Blocks meet at Feature Orchestration.

Neither layer owns the other.

---

# 14. Configuration Model

BusinessLogic™ Blocks provide the canonical behavioral unit exposed to The Anthimeria™ Workbench.

A configuration interface SHOULD expose:

```text
☑ Invoice Approval
```

rather than implementation details such as:

```text
☑ invoice fetcher
☑ billing policy
☑ invoice schema
☑ invoice transaction
☑ Stripe operation
☑ cache helper
```

The Workflow is the meaningful configuration choice.

Its constitution resolves the lower-level requirements.

Thus:

```text
Feature
   ↓
BusinessLogic™ Block
   ↓
Workflow constitution
   ↓
Server Operations + Helpers
```

This is the behavioral equivalent of:

```text
Feature
   ↓
Component Block
   ↓
UI Primitive + Variant
   ↓
Semantic Design Tokens
```

The two systems form separate constitutions:

```text
PRESENTATION CONSTITUTION
UI primitives → Component Blocks

BEHAVIORAL CONSTITUTION
server capabilities → BusinessLogic™ Blocks
```

Feature Orchestration uses both to constitute the application capability.

# 17. Authentication Note

Authentication is a canonical constituent category of the BusinessLogic™ Blocks architecture:

```text
Server Operations
├── Auth
└── Authz
```

The normalized domain inventory explicitly identifies domain Authz files but does not define domain-specific `lib/auth/{domain}` files.

Therefore this specification does not invent such paths.

Workflows MAY depend on the application’s canonical authentication boundary when identity/session establishment is required, but the exact authentication dependency MUST reference the actual architecture-owned Auth implementation rather than a fabricated domain-specific file.

---

# 18. Presentation Files Are Not Workflow Constituents

The normalized ontology also defines:

- Routes;

- Features;

- Page Templates;

- Component Blocks;

- UI Primitives;

- Semantic Design Token files.

Those relationships remain authoritative for the complete Domain Ontology™, but they are **not constituent files of BusinessLogic™ Blocks**.

For example:

```text
app/globals.css
components/ui/palettes.ts
components/blocks/kanban-board.tsx
components/templates/WorkspaceTemplate.tsx
```

may belong to the same ontology as a Workflow, but they do not constitute the Workflow.

They belong to the presentation or application-orchestration side of the architecture.

The boundary remains:

```text
                FEATURE
             /           \
            /             \
PureUI Presentation     BusinessLogic™
       Layer               Blocks
         ↓                   ↓
      Blocks             Workflows
         ↓                   ↓
    Primitives       Server Operations
```

```yaml
    effects: []

  dependencies:
    required: []
```

This manifest does not replace source code.

It records the constitution of the Workflow so that:

- Anthimeria can configure the behavior;

- Virgule can represent it;

- Loaded Vibes can resolve it;

- The Arrangement can retain the required files;

- validation can prove dependency closure;

- documentation can explain the behavior without reverse-engineering imports.


# 21. Canonical Invariants

The following requirements are normative.

1. **A BusinessLogic™ Block is a Workflow.**

2. **A Workflow is a named reusable constitution of application logic.**

3. **A Workflow is formed from existing architecture-owned server operations and helpers.**

4. **A Workflow owns behavioral orchestration, not the implementation responsibilities of its constituents.**

5. **Constituents retain their original architectural identity and ownership.**

6. **Persisted reads remain Fetcher-owned.**

7. **Ordinary CRUD mutation boundaries remain Action-owned.**

8. **Atomic database invariants remain Transaction-owned.**

9. **Authentication remains Auth-owned.**

10. **Authorization remains Authz-owned.**

11. **Provider mechanics remain Integration-owned.**

12. **Runtime schemas remain Schema-owned.**

13. **DTO transformation remains DTO-owned.**

14. **Prisma projections remain Select-owned.**

15. **Cache implementation remains Cache-owned.**

16. **A Workflow MAY coordinate all of those capabilities where its behavior requires them.**

17. **A Workflow MUST NOT copy those capabilities into itself merely to create the appearance of a self-contained unit.**

18. **Provider/network operations MUST remain outside database transactions.**

19. **A Workflow MUST represent meaningful application behavior.**

20. **Trivial CRUD MUST NOT require a ceremonial Workflow.**

21. **A Feature MAY use a Workflow as a reusable unit of application logic.**

22. **A Workflow MAY be reused by multiple Features.**

23. **A Workflow MAY share constituents with other Workflows.**

24. **Removing a Workflow MUST NOT automatically remove shared constituents.**

25. **A configurable Workflow MUST have machine-resolvable dependency closure.**

26. **A selectable Workflow MUST correspond to a supported implementation in The Maximal Template™.**

27. **The normalized ontology defaults are authoritative for the canonical Workflow inventory.**

28. **No additional Workflow is canonical merely because it appears to be useful or belongs to a familiar SaaS domain.**

29. **Exact per-Workflow constituent relationships MUST be explicitly recorded and MUST NOT be fabricated from filenames.**

30. **A Workflow constitution MUST select only valid architecture-owned dependencies.**

31. **BusinessLogic™ Blocks MUST NOT import presentation components, templates, UI primitives, or semantic design-token implementation.**

32. **BusinessLogic™ Blocks and PureUI Presentation Layer™ meet through Feature Orchestration, not through direct ownership of one another.**

# 22. Generator Requirements

Loaded Vibes™ MUST treat BusinessLogic™ Blocks as first-class dependency-bearing application capabilities.

For each selected Workflow it MUST eventually be able to:

1. resolve the canonical Workflow identity;

2. locate its constitution;

3. resolve required constituents;

4. resolve optional constituents;

5. resolve Auth/Authz requirements;

6. resolve persistence requirements;

7. resolve transaction requirements;

8. resolve provider requirements;

9. resolve schema/type/interface requirements;

10. resolve shared dependencies;

11. determine artifact ownership;

12. retain constituents used elsewhere;

13. remove unneeded artifacts only when the complete dependency graph permits removal;

14. reject unresolved dependencies;

15. reject unsupported provider requirements;

16. reject constitution references to nonexistent or noncanonical files;

17. validate that the generated Workflow still represents the selected BusinessLogic™ Block.

# 24. Virgule Requirements

The Virgule™ Application Definition MUST be capable of representing selected BusinessLogic™ Blocks independently from the individual artifacts that satisfy their dependency closure.

The application definition therefore distinguishes:

```text
what behavior the application includes
```

from:

```text
what files are required to implement that behavior
```

This preserves **Constituted, Not Composable** at the configuration level.

---

# 25. Arrangement Requirements

The Arrangement™ Generated Artifact MUST contain real source code.

BusinessLogic™ Blocks MUST resolve to real Workflow source files and real architecture-owned constituent files.

The generated application MUST NOT encode Workflows as giant JSON/YAML implementations or duplicate constituent source into configuration blobs.

Machine-readable definitions describe:

- identity;

- relationships;

- requirements;

- configuration;

- dependency closure.

TypeScript source implements the behavior.

---

# 26. Validation Requirements

A BusinessLogic™ Block passes architectural validation when:

- its Workflow is in the canonical ontology inventory;

- its Workflow file exists;

- its declared domain is correct;

- every declared constituent exists;

- every constituent belongs to an allowed architectural responsibility;

- its exact constitution is machine-readable;

- required Auth/Authz relationships are present;

- transaction boundaries preserve atomicity;

- provider/network operations remain outside Transactions;

- presentation dependencies are absent;

- shared dependencies remain shared;

- Feature consumers resolve correctly;

- dependency closure is complete;

- no generic service abstraction has displaced architecture-owned responsibilities;

- no trivial operation has acquired meaningless Workflow ceremony;

- the generated implementation preserves the behavior represented by the BusinessLogic™ Block.

# 27. Governing Architecture Sentence

> **Routes own URL and HTTP boundaries. Features orchestrate application capabilities. The PureUI Presentation Layer™ constitutes reusable presentation through Component Blocks. The BusinessLogic™ Blocks layer constitutes reusable application logic through Workflows. Fetchers read persisted data. Actions own ordinary CRUD mutation boundaries. Transactions preserve atomic database invariants. Authentication establishes identity. Authorization decides access. Integrations own provider mechanics. DTO Mappers transport approved data shapes. Prisma Selects own canonical projections. Schemas validate runtime input. Helpers retain their precise architectural responsibilities. Workflows arrange those existing capabilities into named reusable application behavior.**

# 29. Canonical Summary

A BusinessLogic™ Block is **not**:

- miscellaneous business logic;

- a generic service;

- an arbitrary function collection;

- a replacement for Fetchers;

- a replacement for Actions;

- a replacement for Transactions;

- a replacement for Auth/Authz;

- a replacement for Integrations;

- a presentation component;

- a container that absorbs its dependencies;

- a mandatory wrapper around CRUD;

- an invented capability not represented by the canonical ontology.

A BusinessLogic™ Block **is**:

- a Workflow;

- a named reusable application behavior;

- a logic orchestration boundary;

- a constitution of existing server operations and helpers;

- a stable behavioral unit;

- dependency-bearing;

- dependency-resolvable;

- reusable by Features;

- configurable through Anthimeria where supported;

- representable through Virgule;

- resolved by Loaded Vibes;

- implemented as real source code in The Arrangement;

- and defined canonically by The Maximal Template™ Domain Library.

The architecture is therefore:

```text
Server Operations + Helpers
            ↓
         constitute
            ↓
BusinessLogic™ Blocks / Workflows
            ↓
   reusable application logic
            ↓
         Features
            ↓
 application capabilities
```

## Governing Principle

> **Server operations and helpers own capabilities. BusinessLogic™ Blocks constitute behavior from those capabilities. Features orchestrate that behavior into application capabilities.**

Or, in the language of the stack:

> **The BusinessLogic™ Block is not the pieces. The BusinessLogic™ Block is the named Workflow constituted by how the pieces act together.**

**Constituted, Not Composable.**
