# New Direction

Going forward, we are headed in a completely new direction with this shit. That mean the old shit is deprecated and superseded by this new epistemology...and It's gonna be called:

### The Codependent Coding™ WebApp Architecture.

We are gonna put everything on one site under that umbrella and we are gonna make the knowledge system into a documentation section like Next.js docs or React.js docs.

The documentation from the existing  Hipster Stack website will be repurposed and the existing content folded in to the new docs.

These docs will become the source of truth for architecture. They will also include end user docs for the generator/CLI tool that configures and generates the template based on this architecture.
### The Hipster Stack™ Technology Stack

This is the generator that transforms a codebase template using a normalized specification and initializes a repository artifact using a cli tool from a custom local node package.

The specification is a generator recipe that is based on specific domain definitions that I handpicked for this project. The 9 customizable SaaS configurations are gonna be default starting points to choose from with each recipe branded as an `Ontology`.

The specification is completely customizable using the web app workspace. The existing Hipster Stack UI for configuring the specification called `The Anthimeria` will be refactored to accommodate for the new direction we are taking.

### The Maximal Template™ Domain Library.

I standardized the default SaaS definitions and functionally decomposed them into modules. I'm branding the modules as libraries called `Simples.` The library from the hipster stack website will be repurposed for this and the existing content folded in.

The libraries are the source of truth for master template. All of the code for every possible configuration of `Simples` from the 9 `Ontologies` are contained in one repository. The generator transforms this codebase when it initializes a new project.

The customized transformed master template that is generated based on the user's configuration of one of the default starter specifications is called the `The Arrangement`
### The Loaded Vibes™ Coding Agent Plugin

 The website will also serve a the custom Codex plugin purpose-built and designed to work with the template. The plugin is also based on the same architecture and is used to enforce the separation of concerns and boundaries

 This plugin will replace the idea of making a dev tool inspired by spec-kit. It consists of governance broken into markdown files. It includes custom agents, skills, instructions, and prompts that ensure the architecture vibes hit right.

 The plugin also features scripts to validate the architecture boundaries and smoke tests to ensure the project directory has the good vibes. Also included are bundled assets to make sure the developer environment has the right vibes too:

 - eslint and prettier configuration files

## Interfaces in Your Faces

`The Anthimeria` is the webapp UI that is used to customize the configurations of the `Ontology` that the generator uses to initialize the `The Arrangement` using the cli tool. It is purpose built to work with The Maximal Template™ Domain Library.

The idea is actually pretty `Simple`:

	We use UI components as the primitives.

The user decides which interfaces (as in which UI) to include and how to customize them. The recipe is generated, normalized, and validated based on those specifications.

### Same Model

1. The user configures their preferences using the web app UI to generate the recipe.
2. That gets normalized and validated and the output is feed into the cli.
3. Then the generator engine uses the recipe to transform the template.
4. The output is the finished artifact for the end user.

### New Features

- `Ontologies` are normalized specifications

  The top layer of `The Anthimeria` configuration UI allows the user to choose from 9 defaults that are starting points based standardized SaaS recipes

- Specifications configure page routes

  The next layer allows the user to select/deselect normalized page routes from a list of all the routes from The Maximal Template™

- Page routes render feature components

  The next layer allows the user to configure the normalized feature components in each page route by selecting/deselecting feature components from a list of all the features from The Maximal Template™

- Features components orchestrate logic and presentation

  The features can be customized by selecting/deselecting options for the logic and presentation layers

- The presentation layer is composed of `Pure UI Blocks`

  The next layer allows the user to configure the normalized block components in each feature component by selecting/deselecting block components and choosing the block variation they want from a list of all the blocks from The Maximal Template™

- `Pure UI Blocks` are composed of UI primitives

  The next layer allows the user to configure the normalized UI primitives in each block component by selecting/deselecting UI primitives and choosing which variant they want from the from a list of all the UI primitives from `The Maximal Template`

  - UI primitives have variants styled with semantic design tokens

   The next layer allows the user to configure the normalized semantic tokens that style each UI primitives by selecting normalized Tailwind CSS color palettes, amination values, Tailwind properties like rounded, padding, margins, and Typography properties like define values for Next.js fonts, typefaces for headings, and so on. These properties are derived from and transform The Maximal Template™ globals.css

- Logic is orchestrated in `BusinessBlocks`

  The next layer allows the user to configure the normalized workflows in each feature component by selecting/deselecting workflows from a list of all the workflows from `The Maximal Template`

   - `BusinessBlocks` are composed of server operations and helpers

   The last layer allows the user to configure the normalized server operations and helpers that compose each workflow by selecting/deselecting normalized server operations and helpers from a list of all server operations and helpers The Maximal Template™

#### Dependency Graphs

Dependencies are normalized and configured automatically so the user cannot configure a template that won't work properly do to broken or missing dependencies.

In practice this mean that selecting or deselecting options in the web app configuration UI automatically deactivates or activates corresponding options that are dependent on whatever option the user is configuring.

Tooltips can be used to warn the user about mandatory dependencies that effect the options available to them.

## S.O.L.I.D. gets Firme

SOLID principles apply beautifully to modern web stack by helping separate user interface, database logic, and third-party services into clean, manageable pieces.

### Single Responsibility Principle (SRP)

> A file or component should do only one thing.

In a full-stack Next.js app, it is easy to accidentally build "giant components" that handle layout, fetch database data, check user permissions, and style things all at once. SRP says to split these up.

- Authentication vs. UI: Do not mix your Clerk auth logic directly inside your layout components. Wrap your app in Clerk providers at the root level, and use simple components just to show or hide UI elements.
- Database vs. Component: Never write raw Prisma queries inside your presentation components. Your components should just call that function.
- Tailwind Cleanliness: If a component needs 50 Tailwind utility classes, extract it into a smaller React component or use shadcn/ui's configuration to keep your main file easy to read.

---

### Open/Closed Principle (OCP)

> You should be able to add new features without changing old code.

This principle is all about building flexible components that can change their behavior using React props or TypeScript types instead of rewriting the inner logic.

- Flexible ShadCN UI Components: Instead of altering the core code of a ShadCN button when you need a new style, use Tailwind's `cn()` utility to pass new classes via props.
- Stripe Payment Webhooks: When Stripe sends an alert that a customer paid, you might want to send an email _and_ update your Neon database. Instead of writing one giant, messy function, use an event system or a clean switch-case block where adding a new action doesn't break the old ones.

---

### Liskov Substitution Principle (LSP)

> Any child component or subclass must work perfectly in place of its parent.

In TypeScript and React, this means your custom wrapper components must strictly honor the HTML standards they are built on.

- Custom Inputs: If you build a custom input component styled with Tailwind, ensure its TypeScript props extend:

```jsx
React.InputHTMLAttributes<HTMLInputElement>
```

- Why it matters: If another developer tries to pass a standard React property like onChange or disabled to your custom component, it must work exactly like a normal HTML input without breaking.

---

### Interface Segregation Principle (ISP)

> Do not force a component to depend on data or features it doesn't use.

TypeScript makes this principle very easy to follow by letting you create small, precise types.

- Cloudinary Images: Imagine you have a TypeScript type called `CloudinaryMedia` that contains 20 fields (URL, height, width, upload date, camera type, location, etc.). If you build a small profile avatar component, do not pass the entire object. Instead, create a smaller type that only asks for the `url` and `alt` text.
- Cleaner Testing: This stops your components from being tightly coupled to giant objects, making them much easier to reuse and test with mock data. [7]

---

### Dependency Inversion Principle (DIP)

> High-level logic should not depend directly on low-level tools. Both should depend on abstractions.

Your stack relies heavily on third-party services (Clerk, Stripe, Cloudinary). If you hardcode these services everywhere, you will have a massive headache if you ever decide to switch to a different provider.

- The Payment Example: Instead of importing the Stripe SDK directly into every single page or component, create a custom service wrapper or a React hook (like `usePayment`).
- Why it helps: Your frontend components only know that they are triggering a payment. If you ever switch from Stripe to Lemon Squeezy or PayPal in the future, you only have to change the code inside that one hook, and your entire frontend remains completely untouched.

## That Bitch is Clean

Robert C. Martin’s (Uncle Bob) Clean Code principles apply here perfectly. While Clean Code was originally written with older languages like Java in mind, its core lessons are universal. In a modern JavaScript ecosystem (Next.js, React, TypeScript, Tailwind CSS), Clean Code helps avoid "spaghetti code" and keeps the template customizable and easy to configure.

### Meaningful Names

> Names should reveal intent. If a name requires a comment, it does not reveal intent.

With TypeScript and React, clear naming stops you from getting confused when passing data between the frontend and the database.

- Avoid Magic Abbreviations: Instead of naming a Prisma database query variable `u`, name it `activePremiumUser`.
- Boolean Naming: For states and flags, always use prefixes like `is`, `has`, or `should`.

    - _Bad:_ `const open = true;` (Open what? Is it open, or does it open something?)
    - _Good:_ `const [isModalOpen, setIsModalOpen] = useState(false);`

- Stripe & Currency: Never just name a variable `price`. Name it `priceInCents` so developers immediately know the data format Stripe expects.

---

### Small Functions & Components

> Functions should do one thing, they should do it well, and they should do it only.

In React and Next.js Server Actions, files can grow into massive monsters very quickly. Clean Code says to break them down.

- The 20-Line Rule: Try to keep your React components and Next.js Server Actions short. If a component is handling a Cloudinary image upload, displaying a user profile, _and_ rendering a Stripe checkout button, it is too big.
- Extract Components: Break that giant page into smaller files like `<AvatarUpload />`, `<ProfileForm />`, and `<CheckoutButton />`.
- No "Side Effects": A function called `fetchUserData()` should only fetch data. It should not accidentally update a user's subscription status in Neon DB or trigger a Stripe charge as a surprise side effect.

---

### Minimal Comments

> Don't use comments to explain bad code. Rewrite the bad code.

TypeScript and Tailwind CSS reduce the need for comments if you use them correctly.

- Let TypeScript Speak: Do not write comments explaining what kind of data an object holds. Use TypeScript interfaces to strictly define the shapes of your Prisma objects or Cloudinary payloads.
- Tailwind Component Extraction: If you have a massive string of Tailwind utility classes that is hard to read, don't write a comment explaining what the style is. Extract it into a well-named shadcn/ui component or use a descriptive variable:

    ```typescript
    // Good: The variable name explains the Tailwind mess
    const primaryButtonStyles = "inline-flex items-center justify-center rounded-md bg-primary px-4 py-2 text-sm font-medium text-primary-foreground shadow transition-colors hover:bg-primary/90";
    ```


---

### One Level of Abstraction per Function

> Code should read like a top-down narrative, moving from high-level ideas to low-level details.

In Next.js Page components, you shouldn't mix high-level layout logic with low-level database configurations.

- Reading Like a Story: A Next.js Page component should look like a simple outline:

    ```tsx
    export default async function DashboardPage() {
      const user = await getCurrentUser(); // High-level concept

      return (
        <DashboardLayoutLayout>
          <UserProfile user={user} />
          <BillingSummary userId={user.id} />
        </DashboardLayoutLayout>
      );
    }
    ```

- Keep Details Hidden: Notice how the page doesn't care _how_ Prisma talks to Neon DB, or _how_ Clerk checks the user's login. Those low-level details are safely hidden inside the `getCurrentUser` function.

---

### Clean Error Handling

> Error handling is important, but if it obscures logic, it is wrong.

With Next.js and Serverless Postgres (Neon), connections can occasionally timeout or fail. You need to handle errors gracefully without making your code unreadable.

- Use Next.js Error Boundaries: Instead of wrapping every single React component in a massive, ugly `try/catch` block that ruins your visual code flow, use Next.js `error.tsx` files.
- Let It Crash (Safely): Let components throw errors naturally if a Prisma query fails. Next.js will automatically catch the error at the page level and show a nice, styled shadcn alert to the user without breaking the rest of the application.

### Authorization

RBAC (Role-Based Access Control)

- Role Hierarchy: Defining structural business roles like Owner, Admin, Manager, Member, and Guest.
- Permission Mapping: Linking static capabilities (e.g., `create:project`, `delete:billing`) directly to specific roles.
- Route & Component Guarding: Blocking unauthorized users from entering entire pages or viewing specific UI elements.
- User-to-Role Assignment: Managing how accounts are bound to roles when invited to a new workspace.

ABAC (Attribute-Based Access Control)

- Dynamic Policy Evaluation: Determining access in real-time based on the user, the resource, and the current environment.
- Contextual Variables: Checking runtime properties like user department, IP address, device type, or time of day.
- Resource Ownership Rules: Enforcing fine-grained logic like "Users can only edit a document if they are the author _and_ the document status is 'Draft'."
- Tenant & Boundary Scoping: Restricting data access based on company dimensions, subscription tiers, or geofences.

### Caching

SSR & ISR (Data Lifecycle & Performance)

- Request Memoization: Reusing fetch responses within a single server render pass to prevent duplicate database calls.
- Data Cache (Server-Side): Storing data across separate user requests and deployments to speed up page loads.
- Full Route Cache: Pre-rendering and caching entire HTML and React Server Component payloads at build or background time.
- Cache Invalidation & Revalidation: Flushing or updating stale cache entries on-demand using tags (`revalidateTag`) or time intervals (`revalidatePath`).
