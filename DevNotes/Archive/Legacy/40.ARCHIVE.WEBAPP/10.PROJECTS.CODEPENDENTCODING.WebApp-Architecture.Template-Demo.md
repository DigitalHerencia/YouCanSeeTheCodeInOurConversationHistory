# The Maximal Template™ Demo Doctrine

## Status

**Canonical user-authored doctrine for The Maximal Template™ demo website.**

This document formalizes the intended application architecture, directory ownership, naming system, presentation model, public-demo behavior, security posture, and integration boundaries for The Maximal Template™.

Where older repository governance, specifications, generated code, agent output, or implementation patterns conflict with this document, **this document wins unless the user explicitly overrides it later**.

The purpose of this document is to eliminate repeated re-explanation of the same architectural intent.

---

# 1. Product Identity

The Maximal Template™ is a **publicly browsable maximal application template and live demonstration of the Hipster Stack architecture**.

It is not merely a landing page, starter kit, dashboard mockup, or collection of unrelated example applications.

It is one coherent superset application that demonstrates reusable architecture across multiple business domains and optional integrations.

The public deployment must make the template's capabilities visible and understandable without requiring authentication.

The application should demonstrate:

- public content surfaces;
- authentication with Clerk;
- application-owned authorization;
- RBAC;
- ABAC;
- tenant-aware access;
- onboarding;
- PostgreSQL row-level security;
- Prisma ORM;
- Neon Serverless PostgreSQL;
- seeded application data;
- provider integrations;
- webhook handling;
- CRUD architecture;
- domain workflows;
- reusable UI primitives;
- reusable grouped UI blocks;
- feature orchestration;
- thin Next.js routes;
- React Hook Form forms;
- typed domain contracts;
- Zod validation;
- optional external-service capabilities.

The public demo should make the architecture itself part of the product demonstration.

---

# 2. Public Demo Model

## 2.1 Public Browsability

The Maximal Template™ public deployment must be browsable without requiring:

- sign-in;
- sign-up;
- onboarding;
- tenant selection;
- organization membership;
- privileged roles.

Application areas such as:

- admin;
- CRM;
- projects;
- support;
- marketing;
- invoicing;
- social;
- portal;
- AI;
- settings;
- onboarding demonstrations;

may be publicly visible as demonstration surfaces.

## 2.2 Public Visibility Does Not Mean Public Mutation Permission

Public route visibility must not weaken application security.

The demo may render seeded or safe demonstration data to signed-out visitors while real protected operations continue to enforce:

1. authentication;
2. authorization;
3. tenant/resource scope;
4. RBAC and/or ABAC;
5. PostgreSQL RLS where applicable;
6. validated mutation input.

A route being publicly visible never grants permission to mutate protected data.

The preferred demonstration model is:

```text
Public visitor
    ↓
publicly browsable seeded/read-only application surface
    ↓
architecture and security behavior visible

Authenticated user
    ↓
identity established by Clerk
    ↓
application authz evaluates role / attributes / resource / tenant
    ↓
scoped persisted read or authorized CRUD mutation
    ↓
Postgres RLS remains the final tenant boundary
```

Authentication is a demonstrated capability, not an admission ticket to the template.

It is not the name for public website pages.

Landing pages, FAQ, terms, contact, features, pricing, and similar pages are **public pages**, not "marketing" architecture.

# 4. Canonical Presentation Architecture

The standard presentation hierarchy is:

```text
components/ui
    ↓
components/blocks
    ↓
features
    ↓
app routes
```

with one explicit exception for form features described later.

## 4.1 UI Primitives

`components/ui/` owns raw reusable UI primitives.

Examples:

- button;
- input;
- textarea;
- select;
- dialog;
- dropdown;
- card;
- badge;
- tabs;
- table primitives;
- skeleton;
- form field primitives;
- toast;
- popover.

UI primitives:

- contain presentation behavior appropriate to the primitive;
- do not own domain logic;
- do not fetch persisted data;
- do not write persisted data;
- do not perform authorization;
- do not own provider integrations.

The primitives must be visually normalized to the Maximal Template™ design system.

---

# 5. Maximal Template™ Visual Language

The public template is **dark-mode only**.

The visual system is neo-brutalist but must not look childish, cartoonish, toy-like, candy-colored, or excessively playful.

The target character is:

- dark;
- industrial;
- technical;
- sharp;
- bold;
- dense;
- deliberate;
- modern;
- slightly aggressive;
- visually distinctive without becoming gimmicky.

Preferred characteristics:

- near-black / charcoal surfaces;
- high-contrast off-white text;
- strong borders;
- restrained accent colors;
- squared or minimally rounded geometry;
- controlled hard shadows;
- clear hierarchy;
- compact technical labeling;
- strong typography;
- deliberate hover and active movement;
- mechanical rather than bouncy motion.

Avoid:

- pastel rainbow palettes;
- excessive pink/yellow/cyan combinations;
- toy-like cards;
- excessive rounded corners;
- cartoonish icon treatment;
- playful bounce animations;
- childish visual metaphors.

The existing BoldKit/shadcn primitives should be reviewed and adapted where necessary rather than blindly accepted.

# 6. Blocks

## 6.1 Block Purpose

`components/blocks/` contains reusable **pure UI compositions** made from UI primitives.

Blocks exist to provide reusable presentation assemblies.

Blocks must not own:

- persisted reads;
- persisted writes;
- provider integrations;
- authentication logic;
- authorization logic;
- domain workflows;
- route logic;
- database logic;
- React Hook Form state;
- application orchestration.

## 6.2 Blocks Are Grouped by UI Category

Blocks are organized by **presentation category**, not by:

- route;
- provider;
- integration;
- authentication vendor;
- business feature implementation.

Examples of valid category-oriented files:

```text
hero-sections.tsx
cta-sections.tsx
feature-sections.tsx
stats-sections.tsx
faq-sections.tsx
testimonial-sections.tsx
pricing-sections.tsx
data-tables.tsx
detail-cards.tsx
dashboard-sections.tsx
invoice-sections.tsx
onboarding-sections.tsx
empty-states.tsx
error-states.tsx
settings-sections.tsx
```

A grouped block file should normally contain multiple related variants.

Example:

```text
hero-sections.tsx
  HeroCentered
  HeroSplit
  HeroWithStats
  HeroMinimal
```

## 6.3 Block Naming

Block filenames use:

```text
lowercase-kebab-case.tsx
```

Named exports use descriptive PascalCase variation names.

Blocks should resemble a reusable BoldKit-style catalog rather than one-off route components.

---

# 7. Features

`features/` owns application orchestration.

A feature exists when a route requires application behavior such as:

- persisted reads;
- CRUD operations;
- authorization;
- authentication-aware behavior;
- workflows;
- provider behavior;
- client-side state;
- application-specific orchestration.

A normal non-form feature may combine:

```text
fetchers
actions
workflows
auth
authz
integrations
cache
types
schemas
blocks
```

## 7.1 Normal Feature Presentation Rule

Normal features consume blocks.

They do not compose arbitrary raw UI primitives directly.

Normal feature shape:

```text
feature
  ↓
application helpers + block composition
```

UI should not be scattered directly through feature orchestration.

---

# 8. Form Feature Exception

Forms are an explicit exception to the normal feature → block rule.

All application forms use **React Hook Form**.

Forms are:

- self-contained feature components;
- composed directly from UI primitives;
- not implemented as blocks;
- not implemented as separate "presentation form" components;
- thinly rendered by page routes.

Examples:

```text
authSignInForm.tsx
authSignUpForm.tsx
newProjectForm.tsx
editProjectForm.tsx
newContactForm.tsx
editContactForm.tsx
```

A form feature may directly import:

```text
components/ui/*
react-hook-form
zod / resolver
relevant action
relevant schema
relevant auth/authz helpers
```

Do not create a reusable block merely to wrap a domain form.

---

# 9. Route Architecture

`app/` owns URL and HTTP boundaries.

Pages should be thin.

They should not contain domain logic, database logic, authorization policy, or complex UI orchestration.

---

# 10. Public Routes

Static public content belongs in:

```text
app/(public)/
```

Examples:

```text
app/(public)/page.tsx
app/(public)/features/page.tsx
app/(public)/faq/page.tsx
app/(public)/pricing/page.tsx
app/(public)/contact/page.tsx
app/(public)/terms/page.tsx
app/(public)/privacy/page.tsx
```

## 10.1 Public Static Page Rule

If a public page has:

- no database read;
- no database write;
- no application workflow;
- no auth/authz orchestration;
- no provider operation;

then it does **not** get a feature component.

The page directly composes reusable blocks.

Example:

```text
page.tsx
  ├── HeroCentered
  ├── FeatureGrid
  ├── StatsSection
  └── CTASection
```

There must not be:

```text
landingFeature
faqFeature
termsFeature
publicMarketingFeature
```

when the page only displays static content.

There must also not be public-page actions, fetchers, types, or schemas without an actual application need.

# 11. Business-Domain Route Pattern

Domain routes follow a consistent list/detail/new/edit pattern when appropriate.

Example using a generic `bullshit` resource:

```text
app/(tenant)/bullshit/page.tsx
app/(tenant)/bullshit/[bullshitId]/page.tsx
app/(tenant)/bullshit/[bullshitId]/edit/page.tsx
app/(tenant)/bullshit/new/page.tsx
```

The corresponding features follow:

```text
bullshitFeature
bullshitClientFeature
bullshitDetailFeature
bullshitDetailClientFeature
bullshitEditForm
bullshitNewForm
```

## 11.1 List Route

```text
app/(tenant)/bullshit/page.tsx
```

renders:

```text
BullshitFeature
```

The feature owns data orchestration.

If search, filtering, sorting, pagination UI, selection, or similar browser behavior is required, that browser-only behavior is segmented into:

```text
BullshitClientFeature
```

## 11.2 Detail Route

```text
app/(tenant)/bullshit/[bullshitId]/page.tsx
```

renders:

```text
BullshitDetailFeature
```

Browser-only interactivity is segmented into:

```text
BullshitDetailClientFeature
```

## 11.3 Edit Route

```text
app/(tenant)/bullshit/[bullshitId]/edit/page.tsx
```

renders a React Hook Form feature:

```text
BullshitEditForm
```

## 11.4 New Route

```text
app/(tenant)/bullshit/new/page.tsx
```

renders:

```text
BullshitNewForm
```

# 12. Suspense, Loading, and Skeletons

## 12.1 Static Routes

For static routes, prefer Next.js route loading behavior:

```text
loading.tsx
```

when a loading state is useful.

## 12.2 Dynamic/Data-Driven Routes

For dynamic routes or routes that perform application reads, the page should wrap the relevant feature in React Suspense.

Example:

```text
<Suspense fallback={<DashboardSkeleton />}>
  <DashboardFeature />
</Suspense>
```

Custom skeletons belong with the relevant feature.

Example:

```text
features/dashboard/dashboardSkeleton.tsx
```

Skeletons should use UI primitives and match the real layout.

# 13. `lib/` Purpose

`lib/` is a reusable application library.

It is **not** a generic `server/` directory.

It contains reusable application operations and helpers used by features and route boundaries.

Canonical structure:

```text
lib/
├── actions/
├── fetchers/
├── db/
│   ├── client.ts
│   ├── selects/
│   ├── dto/
│   └── transactions/
├── auth/
├── authz/
├── integrations/
├── workflows/
├── cache/
├── constants/
└── utils/
```

Do not create unnecessary intermediary hierarchy.

The architecture prefers flat functional decomposition.

---

# 14. Actions

`lib/actions/` owns ordinary persisted CRUD writes.

Actions are not a generic business-logic bucket.

An action should represent database mutation behavior such as:

```text
create
update
delete
restore
archive
```

where those operations are ordinary application mutations.

Actions must:

1. authenticate when required;
2. authorize when required;
3. validate input;
4. preserve tenant/resource scope;
5. perform the database write;
6. use transactions where required;
7. invalidate cache where required.

Non-CRUD business logic belongs elsewhere.

Provider-specific operations do not belong in actions merely because a button triggered them.

---

# 15. Fetchers

`lib/fetchers/` owns **all persisted database reads**.

If code reads from an application table, it is a fetcher unless a more specific database-internal transaction boundary requires otherwise.

Fetchers are strictly read-only.

Typical shapes include:

```text
getAll
getById
getByOrganization
getByIdAndOrganization
getByUser
getByStatus
getByResourceScope
```

Fetchers may:

- authenticate;
- authorize;
- apply tenant/resource filters;
- use Prisma selects;
- use DTO mappers;
- apply safe cache behavior.

Fetchers must never mutate persisted state.

---

# 16. Domain File Naming

Files should communicate both:

1. the business domain;
2. the architectural role.

Preferred examples:

```text
crmActions.ts
crmFetchers.ts
crmTypes.ts
crmSchemas.ts

projectsActions.ts
projectsFetchers.ts
projectsTypes.ts
projectsSchemas.ts

supportActions.ts
supportFetchers.ts
supportTypes.ts
supportSchemas.ts
```

The same concept applies to other shared domain groupings where useful.

Avoid vague names such as:

```text
service.ts
helpers.ts
stuff.ts
mutations.ts
data.ts
manager.ts
processor.ts
```

unless the exact responsibility truly matches the name.

---

# 17. Database Library

`lib/db/` owns Neon and Prisma runtime database infrastructure.

Canonical responsibilities:

```text
lib/db/client.ts
lib/db/selects/
lib/db/dto/
lib/db/transactions/
```

## 17.1 Client

The database client connects Prisma ORM to Neon Serverless PostgreSQL.

Neon database concerns terminate in `lib/db`.

## 17.2 Prisma Selects

`lib/db/selects/` contains reusable Prisma `select` definitions.

They exist to define precise database projection shapes.

## 17.3 DTO Mappers

`lib/db/dto/` contains helpers for mapping persisted/domain records into transport-safe application shapes.

DTO helpers transport data.

## 17.4 Transactions

`lib/db/transactions/` contains reusable atomic transaction helpers.

Transactions coordinate multi-write database invariants and idempotent database behavior.

A transaction helper is not a workflow and is not a webhook.

---

# 18. Prisma Lifecycle

Prisma owns its normal root-level lifecycle.

Canonical structure:

```text
prisma/
├── schema.prisma
├── migrations/
├── seed.ts
└── generated outputs as configured
```

Related root Prisma configuration remains at the repository root where required.

Prisma should be allowed to manage its own:

- schema;
- migration lifecycle;
- generated client artifacts;
- seed lifecycle.

Do not hide Prisma lifecycle inside `lib/`.

---

# 19. Authentication

`lib/auth/` owns Clerk integration and backend authentication helpers.

Clerk belongs in `auth` rather than generic `integrations`.

Examples:

```text
client
session
identity
requireAuth
currentUser
authentication helpers
```

Clerk Organizations are not assumed to own application tenancy.

Authentication answers:

```text
Who is this user?
```

---

# 20. Authorization

`lib/authz/` owns application authorization.

It includes:

```text
roles
permissions
resources
policies
RBAC
ABAC
ownership checks
tenant checks
authorization helpers
```

Authorization answers:

```text
What may this authenticated identity do to this resource in this context?
```

Authentication and authorization remain separate responsibilities.

---

# 21. Application-Owned Tenancy

The application owns organization and membership state unless explicitly changed later.

Clerk authenticates identity.

The application database owns concepts such as:

```text
Organization
Membership
Role
Permission
Resource
Tenant context
```

A typical boundary is:

```text
Clerk identity
    ↓
application user
    ↓
membership
    ↓
organization
    ↓
RBAC/ABAC policy
    ↓
tenant-scoped query/write
    ↓
Postgres RLS
```

---

# 22. Row-Level Security

PostgreSQL RLS is part of the security model and should remain visibly demonstrated by the template.

RLS is defense in depth.

Application authorization does not replace RLS.

RLS does not replace application authorization.

The preferred model is:

```text
Auth
  ↓
Authz
  ↓
Scoped application query
  ↓
RLS
```

---

# 23. Workflows

`lib/workflows/` owns named reusable orchestration boundaries that constitute application logic by arranging existing server operations and helpers according to meaningful behavioral rules, sequencing, conditions, dependencies, and invariants.

Workflow constituents retain their original ownership: fetchers remain fetchers, actions remain actions, transactions remain transactions, authorization remains authorization, and provider mechanics remain integration-owned. Workflows own the behavioral arrangement, do not become a generic service layer, and are not required for trivial CRUD.

A workflow is **not**:

- a persisted read;
- an ordinary CRUD write;
- a Prisma select;
- a DTO mapper;
- a transaction helper;
- authentication;
- authorization;
- provider-specific behavior;
- a webhook route;
- a constant;
- a generic utility.

Workflow directories are organized by business domain and remain shallow.

Example:

```text
lib/workflows/crm/
lib/workflows/projects/
lib/workflows/support/
lib/workflows/marketing/
```

Keep them flat.

Do not introduce:

```text
services/
use-cases/
domain/
application/
managers/
processors/
```

as extra hierarchy unless there is a concrete unavoidable architectural distinction.

---

# 24. Integrations

Provider-specific external-service behavior belongs under:

```text
lib/integrations/{provider}/
```

Examples:

```text
lib/integrations/stripe/
lib/integrations/cloudinary/
lib/integrations/hugging-face/
lib/integrations/sendgrid/
lib/integrations/vercel-blob/
```

Possible provider-specific files include:

```text
client.ts
config.ts
checkout.ts
portal.ts
subscriptions.ts
uploads.ts
images.ts
email.ts
inference.ts
webhook verification helpers
provider-specific adapters
```

## Explicit integration exceptions

```text
Clerk  → lib/auth/
Neon   → lib/db/
Prisma → lib/db/ + root prisma/
```

---

# 25. Webhooks

Webhook HTTP lifecycle belongs in `app/api`.

Canonical shape:

```text
app/api/{provider}/{provider-webhook-path}/route.ts
```

Example:

```text
app/api/clerk/webhooks/route.ts
```

A webhook route may:

1. receive the HTTP request;
2. verify provider authenticity/signature;
3. decode and validate the provider payload;
4. identify the event type;
5. interpret provider-specific event behavior;
6. use provider helpers where appropriate;
7. use transaction helpers for atomic/idempotent persistence;
8. persist required application state;
9. return the provider HTTP response.

Webhook lifecycle code must not be hidden inside a generic workflow or transaction helper.

A transaction helper may support a webhook.

A provider integration helper may support a webhook.

The webhook itself remains an HTTP boundary in `app/api`.

---

`types/` owns shared TypeScript contracts.

Types should be organized by meaningful application domain rather than collapsed into one generic DTO file.

Preferred examples:

```text

types/supportTypes.ts
types/marketingTypes.ts
types/invoicingTypes.ts
types/socialTypes.ts
types/portalTypes.ts
types/adminTypes.ts
types/userTypes.ts
```

Only create types that represent useful shared contracts.

Avoid redundant aliases around generated Prisma types when no architectural value is added.

# 28. Cache, Constants, and Utils

## Cache

`lib/cache/` contains:

- cache tags;
- cache lifetime definitions;
- invalidation helpers;
- related reusable caching infrastructure.

## Constants

`lib/constants/` contains constants.

## Utils

`lib/utils/` contains true generic reusable utilities that do not belong in a more precise architectural category.

If a helper has a more specific home, put it there rather than in `utils`.

# 29. Minimal Hierarchy Rule

The architecture is intentionally flat.

A directory must represent a real responsibility boundary.

Do not add a directory merely because several files can technically be grouped together.

Preferred:

```text
lib/actions/crmActions.ts
lib/fetchers/crmFetchers.ts
```

rather than unnecessary hierarchy such as:

```text
lib/actions/crm/contacts/create/action.ts
```

unless the scale of the real implementation later demands it.

Functional decomposition is preferred over organizational bureaucracy.

Before placing code, classify it using this sequence:

```text

    → app/(public) page + components/blocks

React Hook Form?
    → feature form + components/ui

    → features/

    → lib/fetchers/

    → lib/actions/

Prisma select?
    → lib/db/selects/

DTO mapper?
    → lib/db/dto/

    → lib/db/transactions/

    → lib/auth/

    → lib/authz/

    → lib/integrations/{provider}/

    → app/api/{provider}/.../route.ts

    → lib/workflows/{domain}/

    → lib/cache/

Constant?
    → lib/constants/

    → lib/utils/
```

# 33. Anti-Patterns

The following patterns are considered architectural drift unless explicitly justified:

- public pages placed under `(marketing)`;
- treating public content as the marketing business domain;
- static public pages wrapped in meaningless feature components;
- public-page actions/fetchers with no persisted application behavior;
- blocks containing domain logic;
- blocks containing React Hook Form state;
- blocks containing provider integrations;
- features scattering arbitrary primitive UI;
- form features delegating form UI into blocks;
- CRUD actions becoming generic business services;
- database reads outside fetchers;
- provider operations shoved into actions;
- webhook HTTP lifecycle moved into `lib`;
- Clerk treated as a generic provider integration;
- Neon treated as a generic provider integration;
- Prisma lifecycle hidden under application abstractions;
- workflow directories used as junk drawers;
- generic service layers;
- unnecessary directory nesting;
- types and schemas grouped only by technical mechanism instead of useful domain boundaries;
- admin route groups that accidentally remove `/admin` from the URL;
- public demo routes that require sign-in merely to inspect the template;
- light-mode-first or cartoonish visual styling.

# 35. Core Design Principle

The Maximal Template™ should be easy to understand by looking at filenames and directories.

A developer should be able to infer responsibility from names such as:

```text
crmActions
crmFetchers
crmTypes
crmSchemas
newProjectForm
editProjectForm
projectDetailFeature
projectDetailClientFeature
```

The system prefers obvious responsibility over abstract architectural sophistication.

# 36. Governing Principle

The architecture decomposes application behavior by **what the code actually does**.

If it fetches, it is a fetcher.

If it performs CRUD writes, it is an action.

If it maps DTOs, it is a DTO helper.

If it defines a Prisma projection, it is a select.

If it coordinates an atomic database operation, it is a transaction helper.

If it authenticates, it belongs to auth.

If it authorizes, it belongs to authz.

If it is provider-specific, it belongs to that integration.

If it handles a webhook request, it belongs in the API route.

If it arranges existing server operations and helpers into named reusable application behavior, it is a workflow.

If it only presents UI, it is a primitive or block.

If it orchestrates application behavior, it is a feature.

If it owns the URL, it is a route.

**Do not invent abstractions when the responsibility already has a name.**
