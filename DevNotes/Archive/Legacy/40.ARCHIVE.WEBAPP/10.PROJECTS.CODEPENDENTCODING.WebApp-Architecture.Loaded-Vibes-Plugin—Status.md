## 1. The agent

There is one:

`agents/loaded-vibes-stack.agent.md`

Its job was essentially to become the **stack-aware senior engineer/orchestrator**.

It knows about:

- Next.js 15
- React 19
- Prisma + Neon
- Clerk
- Tailwind v4
- shadcn/ui
- Vitest
- Playwright
- Vercel

It loads a PRD and Tech Requirements, applies the current DevCycle, respects a toolset, performs implementation, maintains artifacts, and asks for human approval around dangerous/high-impact decisions.

Conceptually, that's still useful.

Implementation-wise, it is badly dated.

For example, it says:

> Prefer Server Actions over API routes and colocate data mutations with route groups.

That's **pre-current-architecture Ivan**.

Your current world says something much more precise:

```text
Routes adapt.
Features orchestrate.
Components render.
Fetchers read.
Actions receive mutations.
Workflows coordinate use cases.
Authorization decides.
Transactions preserve invariants.
Integrations own provider mechanics.
Webhooks reconcile external truth.
```

That's the kind of correction the modern plugin needs. Your current master architecture already defines the future plugin in roughly those terms.

# Instructions

There are **18 instruction files**.

These are the policy/governance half of the system.

They're pretty systematic. Most define:

```text
Purpose
Responsibilities
Inputs
Outputs
Success Criteria
Error Handling
Toolset Hook
Traceability
```

That's useful because they aren't merely giant persona prompts. There was already an attempt to distinguish:

**what governs the work**

from

**the request that initiates the work.**

That distinction should absolutely survive.

What should _not_ survive unchanged is some of the generic ceremony.

For example, a lot of phases automatically want:

- TODO updates;
- changelog entries;
- documentation changes;
- stakeholder reports;
- dashboards;
- security scans;
- observability changes;
- formal sign-off.

That made sense in the old “simulate an entire engineering organization” conception.

It clashes with your current doctrine:

> **process proportional to consequence and blast radius.**

The modern version should know these capabilities exist without deploying the entire fucking Pentagon because somebody changed a button label.

# Prompts

There are **19 prompt files**: the 18 corresponding phase prompts plus `template.prompt.md`.

They're basically **execution adapters**.

A prompt identifies:

```text
agent
instruction
toolset
context
desired outcome
human checkpoints
```

That is a strong ancestral concept.

The mistake in the old version is that the **prompt itself carries too much orchestration ceremony**.

Modern Loaded Vibes can make prompts dramatically thinner.

Something closer to:

```text
User intent
    ↓
Skill / workflow classification
    ↓
Relevant architecture context
    ↓
Bounded execution
    ↓
Evidence
```

The architecture should provide the knowledge; the prompt shouldn't have to contain the fucking civilization.

# Toolsets

There are **19 JSONC toolsets**.

These are especially interesting historically because you were trying to express things like:

```json
"allowedOperations": [
  "readFiles",
  "writeFiles",
  "runCLI",
  "callMCP",
  "updateRepo"
]
```

with things like:

```json
"deniedOperations": [
  "deleteRepository",
  "exfiltrateSecrets"
]
```

and:

```text
MCP servers
VS Code extensions
CLI tools
restricted paths
network permission
file-write permission
```

So this is basically the old `.vibes is the syscall table` idea materialized.

The conceptual insight was good.

The problem is that these files are **declarations, not necessarily enforcement**. They can describe what an agent _should_ be able to do without actually being the runtime authority granting those capabilities.

You'd already started figuring that problem out in your later Vibes architecture—the old system eventually acknowledged that some of these boundaries were convention-based rather than cryptographically/runtime enforced.

Modern Loaded Vibes should translate that into whatever Codex's **actual current capability and permission model** supports, and only retain declarative contracts for what can genuinely be checked or used.

Don't cosplay a sandbox.

Either enforce it or describe it accurately.

This is the seed of a very useful:


type of capability.

Not necessarily those exact commands, but that responsibility.

# So where is Loaded Vibes actually at?

I'd characterize it like this:

**Conceptually: surprisingly mature.
Architecturally: superseded.
Content-wise: rich.
Product-wise: not yet a plugin.**

That distinction matters.

You already possess a large amount of the expensive thinking:

```text
context acquisition
governance
work classification
agent role
bounded capability
implementation guidance
validation
review
Git/GitHub delivery
handoff
environment setup
repository inspection
```

Those are almost exactly the capability categories your _current_ canonical architecture says Loaded Vibes should eventually provide: context collection, planning, scoped execution, code/architecture/security review, validation selection, PR/commit preparation, handoff, mechanical architecture validators, smoke tests, and developer-environment assets.

And the current project definition has clarified that the plugin should be a **Codex plugin purpose-built for The Arrangement™ Generated Artifact, carrying governance, agents, skills, instructions, prompts, validation scripts, smoke tests, and developer-environment assets** rather than reviving the old Spec-Kit-ish development product.

That's the big unlock.

## One universal workflow.

- A handful of genuinely different agents.
- Skills for repeatable capabilities.
- Instructions for invariant architecture rules.
- Scripts for things machines can actually prove.
- Mechanical validators for architecture boundaries.
- A small environment package.

Everything deriving from the same canonical architecture instead of independently explaining it seventeen different ways.

That gets you from:

>**“AI Scrum team simulator with 18 ceremonial DevCycles and declared tool permissions”**

to:

>**“A Codex execution environment that already knows how this architecture works and won't casually fuck it up.”**

That second thing is _way_ more valuable to you.

And the beautiful part is you aren't starting from scratch.

You already built the shitty prototype of the idea **before the platform primitives you actually needed existed**.

### Now the primitives exist.

The danger isn't really that _you'll_ fuck it up.

The danger is letting an agent see 3,460 files and decide the assignment is:

> “Modernize all of this.”

**Absolutely fucking not.**

The assignment is:

> **Identify the intent that survived. Discard obsolete machinery. Re-express the surviving intent using the current architecture and current Codex primitives.**

That's a very different operation.

And there is a genuinely nasty little plugin hiding inside that ZIP.
