# The Maximal Template™ Canonical Architecture
## Synopsis

This maximal template is organized around a strict **route → feature → block → primitive** presentation flow and a separate **feature → lib helper** application flow.

At the top level:

- `app/` owns **Next.js routes and HTTP boundaries only**. Pages stay thin and hand off application behavior to features. Webhooks are special route handlers under `app/api/{provider}/.../route.ts`.
- `features/` owns **application orchestration**. Features combine server helpers with presentation blocks. React Hook Form logic lives directly inside the relevant feature. A `.client.tsx` companion exists only when browser-side state or interaction requires one.
- `components/` owns the **presentation layer**:
  - `blocks/` contains reusable UI compositions and is the only UI surface features consume.
  - `nav/` contains headers, footers, sidebars, breadcrumbs, and mobile navigation.
  - `shells/` contains reusable page/application frames.
  - `ui/` contains raw BoldKit/shadcn primitives, which never get imported directly by features.
- `lib/` is the reusable application library. Its folders are classified by what the helper actually does:
  - `actions/` — authenticated/authorized CRUD database writes only.
  - `fetchers/` — all read-only database access.
  - `db/` — Prisma/Neon database infrastructure plus selects, DTO mappers, and transaction helpers.
  - `auth/` — Clerk authentication and server-side identity/session helpers.
  - `authz/` — application-owned RBAC/ABAC roles, permissions, resources, and policies.
  - `integrations/` — provider-specific external-service code, organized by provider; Clerk, Neon, and Prisma are intentionally excluded because they belong to `auth`, `db`, and Prisma's own root lifecycle respectively.
  - `workflows/` — named reusable orchestration boundaries that constitute application logic from existing server operations and helpers. Constituents retain their own responsibilities; domains stay shallow and flat.
  - `cache/`, `constants/`, and `utils/` contain exactly those reusable helper categories.
- `prisma/` owns Prisma's native schema, migrations, and seed lifecycle.
- `generated/` contains generated Prisma artifacts when configured separately.
- `schemas/` contains shared Zod validation schemas.
- `types/` contains shared TypeScript contracts.
- Root configuration files configure Next.js, Prisma, TypeScript, linting, shadcn/BoldKit, environment variables, and request-boundary behavior.

### Architectural flow

```text
URL / HTTP request
        │
        ▼
      app/
        │
        ▼
    features/
      │     │
      │     └───────────────┐
      ▼                     ▼
components/blocks/         lib/
      │                     │
      ▼               ┌─────┼────────────────────────────┐
components/ui/        │     │     │     │     │          │
                  fetchers actions db   auth authz integrations
                                      │
                                   workflows
```

The presentation side follows:

```text
UI primitive
    ↓
block
    ↓
feature
    ↓
page
```

The server/application side follows:

```text
feature
├── fetchers       # reads
├── actions        # CRUD writes
├── db helpers     # selects / DTOs / transactions
├── auth           # authentication
├── authz          # authorization
├── integrations   # provider-specific behavior
├── workflows      # domain logic
├── cache
├── constants
└── utils
```

### Recipe structure

The maximal template contains implementations for all supported recipes, currently represented by domains such as:

```text
CRM
Project Management
Customer Support
Marketing Automation
Invoicing / Expenses
Social Media Scheduling
AI / Micro-SaaS
B2B Client Portal
Internal / Admin Tools
```

Each recipe selects a subset of the maximal template across the same layers:

```text
recipe
├── routes
├── features
├── blocks
├── integrations
├── workflows
├── auth/authz requirements
├── fetchers
├── actions
├── db helpers
├── cache
├── schemas
└── types
```

So the maximal template is **not nine separate applications**. It is one superset implementation that Loaded Vibes can prune and configure according to the selected recipe.

### Core placement rules

```text
Reads persisted data?             -> lib/fetchers/
Writes persisted data?            -> lib/actions/
Prisma select?                     -> lib/db/selects/
DTO mapper?                        -> lib/db/dto/
Transaction helper?               -> lib/db/transactions/
Clerk/authentication?              -> lib/auth/
RBAC/ABAC/authorization?           -> lib/authz/
Provider-specific external code?   -> lib/integrations/{provider}/
Webhook HTTP handler?              -> app/api/{provider}/.../route.ts
Reusable application-logic orchestration? -> lib/workflows/{domain}/
Constant?                          -> lib/constants/
Utility?                           -> lib/utils/
Application orchestration?         -> features/
Browser-only feature behavior?     -> *.client.tsx
React Hook Form?                   -> inside the relevant feature
Reusable UI composition?           -> components/blocks/
Navigation?                        -> components/nav/
Page/application frame?            -> components/shells/
Raw UI primitive?                  -> components/ui/
```

The guiding principle is **functional decomposition with the minimum directory depth necessary**: put a file in the folder that describes what it actually does, keep domains flat, and don't introduce intermediate folders unless they represent a real architectural distinction.

## Recipes

Each recipe answers the same question:

```text
recipe
├── integrations     -> lib/integrations/{provider}
├── workflows        -> lib/workflows/{domain}
├── auth             -> lib/auth
├── authz            -> lib/authz
├── caching          -> lib/cache
├── routes           -> app/*
├── features         -> features/*
├── blocks           -> components/blocks/*
├── nav/shells       -> components/nav + components/shells
├── fetchers         -> lib/fetchers/*
├── actions          -> lib/actions/*
├── db helpers       -> lib/db/{selects,dto,transactions}
├── schemas          -> schemas/*
└── types            -> types/*
```

And the rules are much tighter than how I was framing them before.

### `actions/`

**Writes. CRUD. Period.**

```text
actions/
├── createContact.ts
├── updateContact.ts
├── deleteContact.ts
├── createProject.ts
├── updateProject.ts
└── ...
```

An action:

- authenticates
- authorizes
- performs the database write
- can call transaction helpers
- can call workflow helpers if the mutation needs domain logic
- can invalidate cache

But the action itself is fundamentally a **CRUD write boundary**.

No `calculateRevenueStrategy.ts`.
No `processStripeWhatever.ts`.
No vague “application service” horseshit.

---

### `fetchers/`

**Reads. Every database read. Read-only.**

```text
fetchers/
├── getContacts.ts
├── getContactById.ts
├── getContactByIdAndOrganization.ts
├── getProjects.ts
├── getInvoiceById.ts
└── ...
```

If it looks at persisted application data and does not write it:

**fetcher.**

That is probably the cleanest rule in the whole architecture.

---

### `db/`

Database-specific reusable helpers.

```text
db/
├── client.ts
│
├── selects/
│   ├── contactSelect.ts
│   ├── projectSelect.ts
│   └── ...
│
├── dto/
│   ├── contactDto.ts
│   ├── projectDto.ts
│   └── ...
│
└── transactions/
    ├── createInvoiceTransaction.ts
    ├── processWebhookEventTransaction.ts
    └── ...
```

These are not independent application operations.

They're helpers used **by fetchers/actions/features/etc.**

And this is also where the special database integrations terminate:

```text
Neon -> db/
Prisma runtime client -> db/
Prisma schema/migrations/generation -> root prisma/
```

Which is much cleaner than pretending Neon deserves a random `integrations/neon/` directory when its entire purpose here is the database.

---

### `integrations/{provider}`

If it exists because some external provider exists, it goes with that provider.

```text
integrations/
├── stripe/
│   ├── client.ts
│   ├── checkout.ts
│   ├── customerPortal.ts
│   ├── subscriptions.ts
│   └── ...
│
├── cloudinary/
│   ├── client.ts
│   ├── upload.ts
│   └── transformations.ts
│
├── hugging-face/
│   ├── client.ts
│   ├── inference.ts
│   └── embeddings.ts
│
└── sendgrid/
    ├── client.ts
    └── email.ts
```

With the explicit exceptions:

```text
Clerk -> auth/
Neon -> db/
Prisma -> db/ + root prisma/
```

Those are exceptions because their **application responsibility is more meaningful than their vendor identity**.

That is the pattern I was missing.

### `auth/`

Clerk lives here because Clerk **is your authentication implementation**.

```text
auth/
├── client.ts
├── session.ts
├── currentUser.ts
├── currentOrganization.ts
├── requireAuth.ts
└── ...
```

Not:

```text
integrations/clerk/
```

because then you're classifying it according to *who sold it to you* instead of *what it does*.

---

### `authz/`

Authorization stays completely separate.

```text
authz/
├── roles.ts
├── permissions.ts
├── policies.ts
├── resources.ts
└── ...
```

RBAC, ABAC, tenant boundaries, resource ownership.

Nothing Clerk-specific unless you're adapting Clerk identity information into those policies.

## Webhooks are route handlers

This was another distinction I was muddying.

The webhook **is the HTTP boundary**, so it belongs in `app/api`.

```text
app/
└── api/
    ├── stripe/
    │   └── webhook/
    │       └── route.ts
    │
    └── clerk/
        └── webhook/
            └── route.ts
```

That handler owns the request lifecycle:

```text
receive request
    ↓
verify provider signature
    ↓
decode / validate payload
    ↓
interpret event
    ↓
perform idempotent write
    ↓
return provider response
```

And it can reach downward into reusable helpers:

```text
route.ts
├── auth/provider verification if applicable
├── integrations/stripe/*
└── db/transactions/*
```

But the transaction helper is **not the webhook**.

Likewise, Stripe-specific parsing/signature/event helpers belong under:

```text
lib/integrations/stripe/
```

because they're Stripe shit.

That distinction is clean.

---

### `workflows/`

This is the remainder after everything with a more precise functional name has been removed.

```text
workflows/
├── crm/
├── projects/
├── support/
├── marketing/
├── invoicing/
├── social/
├── ai/
├── portal/
└── admin/
```

And **flat means flat**.

Good:

```text
workflows/
└── crm/
    ├── advanceDealStage.ts
    ├── calculatePipelineValue.ts
    ├── detectStalledDeal.ts
    └── buildSalesActivity.ts
```

Not:

```text
workflows/
└── crm/
    └── pipeline/
        └── services/
            └── domain/
                └── ...
```

If we can't explain why another directory exists, **we don't create the fucking directory.**

The classification rule becomes:

```text
READ DATABASE?
    fetchers/

WRITE DATABASE?
    actions/

PRISMA SELECT?
    db/selects/

DTO MAPPER?
    db/dto/

TRANSACTION HELPER?
    db/transactions/

AUTHENTICATION?
    auth/

AUTHORIZATION?
    authz/

PROVIDER-SPECIFIC?
    integrations/{provider}/

WEBHOOK HTTP HANDLER?
    app/api/{provider}/.../route.ts

CONSTANT?
    constants/

UTILITY?
    utils/

DOMAIN LOGIC THAT IS NONE OF THE ABOVE?
    workflows/{domain}/
```

That is the whole fucking classifier.

And it's actually good.

## Feature composition

The other half is equally strict.

A feature is where those helpers become an actual application capability.

```text
Feature
├── fetcher(s)
├── action(s)
├── workflow helper(s)
├── auth/authz helper(s)
├── cache helper(s)
├── React Hook Form logic when necessary
└── blocks
```

No separate form architecture.

If the feature is a form:

```text
features/
└── crm/
    └── contactEditorFeature.tsx
```

then `contactEditorFeature.tsx` can contain:

```text
React Hook Form
Zod hookup
submission behavior
action invocation
feature orchestration
block composition
```

It does **not** create:

```text
forms/
form-hooks/
form-fields/
form-services/
```

just because we learned how to create directories.

And the presentation boundary remains:

```text
ui primitive
    ↓
block
    ↓
feature
    ↓
page
```

A feature can import:

```text
components/blocks/*
```

It **cannot** reach into:

```text
components/ui/*
```

If the feature needs a composition that doesn't exist:

**make a block.**

That also means nav and shells need to obey the same presentation discipline. They're reusable structural presentation, not feature logic:

```text
components/
├── blocks/
├── nav/
│   ├── header.tsx
│   ├── footer.tsx
│   ├── sidebar.tsx
│   └── mobileNav.tsx
├── shells/
│   ├── appShell.tsx
│   ├── marketingShell.tsx
│   └── authShell.tsx
└── ui/
```

The pattern is **functional decomposition first, minimal hierarchy second, orchestration in features, presentation through blocks, routes at the edge**.


And the non-negotiable presentation chain is:

```text
components/ui/*
        ↓
components/blocks/*
        ↓
features/*
        ↓
app/**/page.tsx
```

`nav/` and `shells/` sit alongside blocks because they're reusable **structural presentation**, not application features and not raw primitives.
