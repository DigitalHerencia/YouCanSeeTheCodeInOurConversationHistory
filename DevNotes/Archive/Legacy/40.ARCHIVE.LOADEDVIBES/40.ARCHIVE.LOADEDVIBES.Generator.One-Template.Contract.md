# Loaded Vibes One-Template Generator Contract

## Core Contract

Loaded Vibes has one canonical maximal white-label application template.

It must not maintain separate application source trees for product presets or optional capability modules when those sources can live coherently inside the maximal template.

```text
ONE MAXIMAL WHITE-LABEL TEMPLATE
        │
        ├── canonical Hipster Stack patterns
        ├── supported route surfaces
        ├── supported integrations
        ├── provider boundaries
        ├── reusable application infrastructure
        └── local agent context
                    │
                    ▼
            packages/core
                    │
          resolve + plan
          retain + remove
          deterministic transforms
                    │
                    ▼
          GENERATED REPOSITORY
```

## Source-of-Generation Rule

The executable template source lives inside LoadedVibes.

A generated project must not require a separate Vibes repository, runtime sync from Vibes, or Vibes-derived source resolution.

The source relationship is:

```text
DevNotes
  knowledge plane
      │
      ▼
LoadedVibes/template/
  executable canonical implementation
      │
      ▼
Loaded Vibes generator
      │
      ▼
Generated repository
```

The historical Vibes repository may remain relevant as provenance while it exists, but it is not part of the active generation architecture.

## Template Singular Rule

The target repository uses:

```text
template/
```

not:

```text
templates/golden
templates/modules
```

There is one template.

Optionality is modeled as ownership metadata and deterministic retain/remove behavior over that maximal source.

## No Duplicate Module Source Trees

A capability such as Cloudinary, Mapbox, Stripe Connect, or a sample domain may own a set of files in the maximal template.

The generator may later use a manifest such as:

```text
capability: cloudinary
files:
  app/(tenant)/uploads/**
  app/api/cloudinary/**
  components/uploads/**
  features/uploads/**
  lib/actions/uploadActions.ts
  lib/fetchers/mediaFetchers.ts
  lib/workflows/uploadWorkflows.ts
  lib/integrations/cloudinary/**
  lib/webhooks/cloudinaryWebhookWorkflow.ts
  schemas/uploadSchemas.ts
  schemas/cloudinaryWebhookSchemas.ts
  types/uploadTypes.ts
  prisma/migrations/0007_media_assets/**
```

The manifest describes ownership of files already present in the maximal template.

It does not require a second capability source tree containing duplicate application code.

## First-Phase Rule

Do not design a generalized module framework before the maximal template is complete and coherent.

Phase one is:

```text
MASTER TEMPLATE
  everything supported exists
  everything works together
  every ownership boundary is obvious
```

Phase two teaches the generator to retain and remove supported capabilities.

## Shared Core Rule

`packages/core` is the deterministic production engine shared by every interface.

It owns concerns such as:

- catalog metadata;
- configuration defaults and normalization;
- dependency resolution;
- generation planning;
- materialization;
- pruning;
- structured transforms;
- generated manifests;
- project loading and state;
- installation lifecycle;
- Prisma lifecycle;
- Git lifecycle;
- create/add/explain/doctor application commands.

Do not create a second generator engine for the website or CLI.

## Thin Interface Rule

The target relation is:

```text
Website Configurator ─┐
                      │
CLI ──────────────────┼──► Core ─► Template ─► Project
                      │
loadedvibes.json ─────┘
```

The CLI is a thin terminal adapter.

The website is a thin visual adapter.

Neither interprets the configuration independently.

## Recipes Rule

The old `packages/recipes` abstraction is not part of the target architecture.

Any reusable behavior it currently contains should be absorbed into:

```text
packages/schema
packages/core/src/config
packages/core/src/catalog
```

before the package is removed.

Named product shapes may remain as configuration presets or default bundles, but they must not become separate architecture or template source trees.

## Determinism

Identical normalized configuration against the same Loaded Vibes version must produce the same generation plan and materially equivalent repository output.

All removal and transformation rules must be inspectable and explainable.

## Generated Provenance

Generated repositories should record enough provenance to identify:

- Loaded Vibes version;
- template version or revision;
- normalized configuration;
- retained supported capabilities;
- deterministic transformations applied.

Provenance describes generation by Loaded Vibes rather than a dependency on a continuing Vibes upstream repository.

## Invariant

> **One application architecture, one maximal source template, one configuration model, and one production engine.**
