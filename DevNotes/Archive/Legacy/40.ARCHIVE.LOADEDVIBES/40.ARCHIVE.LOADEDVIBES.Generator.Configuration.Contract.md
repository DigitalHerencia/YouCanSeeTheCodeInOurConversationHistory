# Loaded Vibes Generator Configuration Contract

## Purpose

Define the boundary between what Loaded Vibes has already decided and what a user may configure.

The generator must not convert doctrinal invariants into preference prompts.

## Rule 1: Fixed Architecture Is Not Configuration

The following belong to the Loaded Vibes platform kernel and must not be presented as ordinary opt-in stack choices:

- TypeScript
- Next.js App Router
- React Server Components by default
- pnpm
- Zod
- Prisma
- Neon/PostgreSQL
- Clerk identity
- local application users
- Organizations and Memberships
- custom capability RBAC
- RLS where tenant isolation requires it
- Fetchers
- Server Actions
- Workflows
- Transactions
- Integration Adapters
- Webhook processors
- DTO mappers
- Selects
- shadcn primitives
- Vercel deployment assumptions
- route → feature → block/component layering
- auth/authz boundary
- server-operations boundary

The generator exists in part to make these decisions once and reuse them.

## Rule 2: Configuration Must Change Generated Output Meaningfully

A setting belongs in the configuration surface only when Loaded Vibes can deterministically explain and implement its effect.

A setting must have a defined contribution such as:

- retained or removed files;
- structured configuration transforms;
- dependency contributions;
- environment requirements;
- route-surface changes;
- schema or data-model contributions;
- validation contributions;
- generated documentation or context changes.

Do not expose a checkbox whose removal behavior is incomplete or whose output cannot be described precisely.

## Rule 3: One Configuration Model

Interactive CLI prompts, CLI flags, the web configurator, and `loadedvibes.json` are adapters over the same configuration schema.

```text
Web UI ──────────────┐
CLI prompts ─────────┤
CLI flags ───────────┼──► normalized configuration ─► packages/core
loadedvibes.json ────┘
```

No interface may maintain an independent interpretation of the configuration.

## Project Configuration

The project-level configuration surface may include:

```text
name
directory
packageName
description
gitInit
installDependencies
```

These configure generation mechanics and project identity without changing the application architecture.

## Product Shape

Supported product shapes may include:

```text
B2B SaaS
Client Portal
Marketplace / Platform
Internal Tool
Bare Golden App
```

Product shape is a starting configuration over one architecture.

It is not a template selector and must not create five independent application architectures.

A shape may set sensible defaults for capabilities, route surfaces, sample content, or identity while still resolving through the same generator.

## Product Capabilities

Candidate configurable capabilities include:

```text
Organizations
Invitations
Onboarding
Billing
Stripe Connect
Marketing
Sample Domain
Presentation Catalog
Agent Governance
```

A capability may be configurable only after its full retain/remove boundary is known.

Dependencies must resolve automatically rather than forcing the user to understand the internal capability graph.

## Product Identity

Supported identity fields may include:

```text
productName
description
brandName
domainVocabulary
```

Domain vocabulary must remain bounded.

It may rename generic generated concepts where the transformation is safe and explicit, but it must not pretend to synthesize an entire business domain.

Example:

```text
primaryResource:
  singular: Shipment
  plural: Shipments
```

## Visual Direction

Visual configuration should remain semantic rather than exposing arbitrary design-system internals.

Supported axes may include:

```text
colorFamily
radius
density
navigation
typographyTreatment
```

Loaded Vibes' own interface remains dark-only.

Generated applications may have independent theme capabilities if explicitly supported by the generated application architecture.

## Vocabulary Contract

Do not use configuration language that implies the user is selecting core architecture.

### Prohibited or misleading

```text
Choose your stack
Choose your architecture
```

### Preferred

```text
Configure your project
Golden Foundation
Product Shape
Capabilities
Product Identity
Visual Direction
Generated Output
```

## CLI Contract

The CLI is the authoritative execution adapter for generator behavior.

Target command family:

```text
loaded-vibes create <project>
loaded-vibes create <project> --config loadedvibes.json
loaded-vibes add <capability>
loaded-vibes explain
loaded-vibes doctor
```

Command names may evolve during implementation, but all commands must call the shared core engine rather than reproduce generation logic in the CLI package.

## Web Configurator Contract

The web application is a visual configuration workbench.

It must:

- represent the same configuration schema as the CLI;
- show the fixed Golden Foundation without presenting it as optional;
- expose only supported configurable surfaces;
- show what the generated output will include;
- produce a configuration or command usable by the CLI;
- remain dense and developer-oriented rather than adopting consumer startup-wizard language.

The web app is not a second generator implementation.

## Generated Output Review

Before generation, the user should be able to inspect a plan describing:

- fixed foundation;
- selected product shape;
- selected capabilities;
- resolved dependencies;
- identity and visual configuration;
- files or surfaces retained and removed where useful;
- remaining provider setup.

The review must reflect the actual production plan computed by the core engine.

## Invariant

> **Loaded Vibes asks the user only about decisions that have not already been made by Loaded Vibes.**
