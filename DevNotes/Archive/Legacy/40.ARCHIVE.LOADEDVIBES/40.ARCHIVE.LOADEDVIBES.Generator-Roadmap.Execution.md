# Loaded Vibes Generator Roadmap

## Objective

Implement Loaded Vibes as a self-contained deterministic project initializer around one maximal white-label application template.

This roadmap replaces the earlier Vibes-upstream, recipe-package, preset-first, and module-source-tree sequence.

The current design order is deliberately simple:

```text
1. template/
      ↓
2. schema + core generator
      ↓
3. website landing + /configure + docs
      ↓
4. CLI polish
      ↓
5. ship Loaded Vibes MVP
```

## Phase 1: Build and Freeze `template/`

Establish one maximal white-label application inside the LoadedVibes repository.

Work:

- move the canonical application source toward singular `template/`;
- absorb supported capability source that currently lives under separate module/template structures;
- remove active dependence on a separate Vibes repository;
- preserve the correct internal application architecture rather than reorganizing it for aesthetics;
- complete supported route surfaces, integration boundaries, server operations, presentation, context, and agent guidance;
- make the generated UI look like an actual product rather than architecture documentation;
- identify capability ownership without implementing a generalized module framework yet.

**Exit condition:** the maximal application exists in one source tree, is coherent as a complete application, and provides the canonical source for future generated repositories.

## Phase 2: Converge Schema and Core Generator

Make one normalized configuration model and one deterministic production engine.

### `packages/schema`

- define the versioned `loadedvibes.json` contract;
- model project settings, product shape, capabilities, identity, visual direction, and supported technical configuration;
- ensure fixed platform-kernel decisions cannot become ordinary opt-out switches.

### `packages/core`

- centralize defaults and normalization;
- resolve capability dependencies;
- compute generation plans;
- define file ownership;
- materialize the maximal template;
- prune excluded capabilities;
- apply structured deterministic transforms;
- write generation provenance;
- support create/add/explain/doctor behavior;
- own install, Prisma, and Git lifecycle behavior.

### Cleanup

- absorb useful behavior from `packages/recipes` into schema/core catalog/config concerns;
- remove `packages/recipes` after its useful logic has been incorporated;
- remove duplicated module-source concepts after their source is represented in the maximal template.

**Exit condition:** the same normalized configuration always produces the same explainable generation plan and repository output.

## Phase 3: Rebuild the Web Experience Around the Tool

Split the current website into three surfaces:

```text
/             developer-oriented landing
/configure    visual configuration workbench
/docs/*       end-user documentation
```

Work:

- reduce marketing emphasis;
- make the configurator the dominant product experience;
- show the fixed Golden Foundation without presenting it as optional;
- expose only supported configuration;
- provide product shape, capabilities, identity, and bounded visual-direction controls;
- show a generated-output plan and useful live preview;
- produce a `loadedvibes.json` representation or CLI command from the same schema;
- render canonical user documentation from root `docs/`.

Do not add accounts, project-management SaaS, or a hosted generation backend unless a later product need justifies them.

**Exit condition:** a developer can visually configure a supported project and hand the resulting recipe directly to the CLI/core production path.

## Phase 4: CLI Polish and Developer Workflow

Keep the CLI as the primary execution interface.

Target command family:

```text
loaded-vibes create <project>
loaded-vibes create <project> --config loadedvibes.json
loaded-vibes add <capability>
loaded-vibes explain
loaded-vibes doctor
```

Work:

- keep the CLI thin over `packages/core`;
- support interactive and non-interactive creation;
- validate destinations safely;
- initialize Git optionally;
- install dependencies optionally;
- report exact generation plans and failures;
- make `explain` surface architecture/configuration provenance without polluting the generated UI;
- make `doctor` identify actionable local/provider setup gaps;
- validate Windows and PowerShell path behavior explicitly.

**Exit condition:** the CLI can reliably materialize supported projects from interactive input or `loadedvibes.json` using the same core plan as the website.

## Phase 5: MVP Release

Package and ship the self-contained Loaded Vibes system.

Work:

- validate packed-package behavior;
- ensure published content excludes private notes, credentials, caches, and workbench-only artifacts;
- define release versioning and provenance;
- verify representative generated repositories;
- document provider setup left to the developer;
- confirm generated repositories contain the context and agent boundaries required for downstream Codependent Coding work.

The MVP success test is not the number of configuration switches.

It is:

> **How much repetitive foundational work is gone after generation?**

**Exit condition:** a developer can create a supported white-label application, understand what Loaded Vibes generated, perform remaining provider setup, and begin product-specific implementation without restructuring the foundation.

## Deferred Until After MVP

Do not let these expand the current sequence:

- arbitrary plugin systems;
- general-purpose template marketplaces;
- independent source modules for every capability;
- hosted user accounts or project management;
- automatic upgrades of heavily modified generated repositories;
- provider provisioning that is less reliable than explicit setup;
- configuration options without complete composition/removal behavior.

## Current Next Action

Complete the maximal `template/` design and implementation boundary first.

That is the stable object the generator will learn to transform.
