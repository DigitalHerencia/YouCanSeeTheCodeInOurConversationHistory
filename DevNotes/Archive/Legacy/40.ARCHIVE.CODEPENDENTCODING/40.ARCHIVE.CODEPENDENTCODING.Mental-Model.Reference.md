# Recommended mental model

You actually have **4 distinct concerns**:

## 1. Reference model

Static or slowly changing facts about your ecosystem.

Examples:

* ChatGPT exists
* ChatGPT browser exists
* Copilot CLI exists
* Obsidian exists
* GitHub repo exists
* Markdown is a file type
* PowerShell can operate on local files
* n8n can orchestrate workflows

This belongs in relational tables.

## 2. Capability model

What each entity can do, under what constraints.

Examples:

* ChatGPT Android supports voice input
* Copilot in VS Code supports inline code generation
* CLI tools are scriptable
* Cloud tools may support webhooks or APIs
* Obsidian stores markdown locally
* Google Drive supports shared file storage but not arbitrary code execution

Also relational, but with careful normalization.

## 3. Decision model

Rules for choosing the right tool/path for a task.

Examples:

* If task requires hands-free capture on mobile, prefer ChatGPT Android
* If task requires deterministic file manipulation on local machine, prefer PowerShell or CLI
* If task requires cross-app automation, consider n8n or Power Automate
* If task output is a spec for a repo, store as markdown artifact and link to project/repo

This is **not** a table-first thing. This is either:

* rule engine in app code
* decision graph
* weighted scoring system
* hybrid of rules + ranking

## 4. Execution history

What happened in reality.

Examples:

* user initiated task X
* decision engine selected path Y
* agent Z drafted artifact A
* artifact saved to Obsidian
* repo PR created
* workflow failed at node 4

This is event/run logging.

# What I would build

I would not start with “decision tree tables.”

I would start with a **three-layer data model**:

## A. Catalog layer

What exists.

Tables:

* `tools`
* `platforms`
* `tool_surfaces`
* `capabilities`
* `file_types`
* `storage_targets`
* `automation_engines`

## B. Planning layer

How decisions are made.

Tables:

* `task_types`
* `decision_criteria`
* `decision_rules`
* `workflow_templates`
* `workflow_steps`

## C. Runtime layer

What happened.

Tables:

* `task_runs`
* `decision_runs`
* `execution_runs`
* `artifacts`
* `artifact_links`
* `run_events`

That is the clean split.

model Tool {

  DOCUMENT

## 3) `tool_surfaces`

This is the important one.

A tool does not just “have columns.”
A tool exists on one or more surfaces, and each surface may have different constraints.

Examples:

* ChatGPT × Browser
* ChatGPT × Windows Desktop
* ChatGPT × Android
* Copilot × GitHub Browser
* Copilot × VS Code
* Codex × Windows App

```prisma
model ToolSurface {
  id                    String                 @id @default(cuid())
  toolId                 String
  platformId             String
  surfaceName            String?
  status                 SurfaceStatus         @default(ACTIVE)
  notes                  String?

  tool                   Tool                   @relation(fields: [toolId], references: [id], onDelete: Cascade)
  platform               Platform               @relation(fields: [platformId], references: [id], onDelete: Cascade)

  capabilities           ToolSurfaceCapability[]
  inputFileTypes         ToolSurfaceFileType[]  @relation("surface_input_filetypes")
  outputFileTypes        ToolSurfaceFileType[]  @relation("surface_output_filetypes")

  decisionCandidates     DecisionRule[]         @relation("RulePreferredSurface")
  taskRuns               TaskRun[]

  createdAt              DateTime               @default(now())
  updatedAt              DateTime               @updatedAt

  @@unique([toolId, platformId, surfaceName])
}
```

This table is where your matrix becomes real.

You were right to bring in file types. They matter because they strongly shape routing.

Examples:

* yaml
* ts
* tsx
* mdx

```prisma
model FileType {
  id              String                @id @default(cuid())

  extension       String
  mimeType        String?
  name            String
  description     String?

model ToolSurfaceFileType {
  id              String         @id @default(cuid())
  toolSurfaceId    String
  fileTypeId       String
  direction        FileDirection
  supportLevel     SupportLevel   @default(NATIVE)
  notes            String?

  toolSurface      ToolSurface    @relation(fields: [toolSurfaceId], references: [id], onDelete: Cascade)
  fileType         FileType       @relation(fields: [fileTypeId], references: [id], onDelete: Cascade)

  createdAt        DateTime       @default(now())
  updatedAt        DateTime       @updatedAt

  @@unique([toolSurfaceId, fileTypeId, direction])

enum FileDirection {
  INPUT
  OUTPUT
}

enum SupportLevel {
  NATIVE
  INDIRECT
  EXPORT_ONLY
  IMPORT_ONLY
  UNSUPPORTED
}
```

Now your system can answer:

* “Which surfaces can output markdown?”
* “Which tools can consume JSON?”
* “Which platform supports TSX editing plus repo write?”

That’s the real payoff.

  name            String

  NUMBER
  STRING

## 9) `decision_rules`

Do not hardcode “tree nodes” as some brittle giant hierarchy at first.

Start with weighted rules.

```prisma
model DecisionRule {
  id                    String                   @id @default(cuid())
  slug                  String                   @unique
  name                  String
  taskTypeId            String
  preferredSurfaceId    String?
  score                 Int                      @default(0)
  rationale             String?

  taskType              TaskType                 @relation(fields: [taskTypeId], references: [id], onDelete: Cascade)
  preferredSurface      ToolSurface?             @relation("RulePreferredSurface", fields: [preferredSurfaceId], references: [id], onDelete: SetNull)
  criteria              DecisionRuleCriterion[]

  createdAt             DateTime                 @default(now())
  updatedAt             DateTime                 @updatedAt
}

model DecisionRuleCriterion {
  id                    String                @id @default(cuid())
  decisionRuleId        String
  criterionId           String
  operator              RuleOperator
  expectedValue         String
  weight                Int                   @default(1)

  decisionRule          DecisionRule          @relation(fields: [decisionRuleId], references: [id], onDelete: Cascade)
  criterion             DecisionCriterion     @relation(fields: [criterionId], references: [id], onDelete: Cascade)

  @@unique([decisionRuleId, criterionId, operator, expectedValue])
}

enum RuleOperator {
  EQ
  NEQ
  GT
  GTE
  LT
  LTE
  CONTAINS
  IN
}
```

That gives you a rules engine without pretending SQL is a personality.

# How the decision tree should actually work

This is the part that needs to be straightened out.

You said the decision tree sits on top of the ERM.
That is basically correct, but more precisely:

## Better formulation

The **relational model** stores:

* tools
* platforms
* surfaces
* capabilities
* file type compatibility
* workflow templates
* prior runs

The **decision engine** queries that model to:

* filter valid candidates
* score the candidates
* recommend the best path
* instantiate a workflow

So the ERM is not the thing “running.”
It is the **decision substrate**.

The decision layer is application logic.

That is the grown-up version of the idea.

# Example flow

Task: “Create a PRD from a voice conversation and store it in the correct repo.”

## Inputs

* user on Android
* voice-first
* output must be markdown
* final destination is a code repo
* wants some AI drafting
* human review required

## Query logic

1. Find surfaces supporting voice input
2. Prefer mobile capture surfaces
3. Find tools/surfaces that can output structured markdown
4. Find workflow templates that end in repo artifact creation
5. Score candidates:

   * friction
   * quality
   * determinism
   * repo compatibility
   * reviewability

## Decision result

* Capture: ChatGPT Android
* Structuring: ChatGPT Browser or Desktop after transfer
* Drafting: Codex/Copilot/ChatGPT depending task type
* Save: local repo / GitHub repo
* Orchestration: PowerShell or n8n, depending whether local or cross-service

## Output

* task run record
* artifact: `prd.md`
* artifact links to repo path
* event log for auditability

That’s what this should do.

# Practical recommendation for phase 1

Do not build the whole cathedral immediately, because that’s how people end up building schema fan fiction instead of software.

## Phase 1 schema

Start with only these tables:

* `tools`
* `platforms`
* `tool_surfaces`
* `capabilities`
* `tool_surface_capabilities`
* `file_types`
* `tool_surface_file_types`
* `task_types`
* `task_runs`
* `artifacts`

Skip:

* complex decision rules
* workflow templates
* deep execution event logs

At first, the decision engine can live in TypeScript:

* fetch candidate surfaces
* filter by required criteria
* rank with simple heuristics
* return recommendations

Once you’ve done 20 to 50 real task runs, then you formalize the rules into tables.

That’s the correct order. Data first, then heuristics, then abstraction. Humans love inverting that and acting surprised when everything sucks.

Given your stack, I’d structure it like this:

* Prisma models in your main app schema
* seed files for:

  * platforms
  * tools
  * capabilities
  * file types
* server-only fetchers:

  * `lib/fetchers/tool-surfaces/*`
  * `lib/fetchers/decision-engine/*`
* server actions:

  * `lib/actions/task-runs/create-task-run.ts`
  * `lib/actions/artifacts/create-artifact.ts`
* typed DTOs for decision results
* Zod schemas for task input criteria

Example app boundary:

* UI collects task context
* server action creates a `taskRun`
* decision service scores surfaces/tools
* user sees recommended workflow
* execution writes artifacts + status

# What not to do

## Don’t:

* make one giant `entities` table for everything
* store capabilities as a comma-separated text blob
* encode your whole decision tree in JSON on day one
* confuse platforms, tools, and storage targets
* pretend Obsidian, GitHub repo, and ChatGPT are the same type of thing
* make “cloud” a vague magical property instead of a specific execution surface

# Clean taxonomy

If I were formalizing your universe, I’d classify like this:

## Tool

A named product or system.
Examples: ChatGPT, Copilot, Obsidian, n8n, PowerShell, Google Drive

## Platform

Where the tool is accessed or runs.
Examples: Browser, Android, Windows Desktop, CLI, VS Code, Cloud Hosted

## Surface

A specific tool-platform pairing.
Examples: ChatGPT Android, Copilot VS Code, Codex Browser

## Capability

Something a surface can do.
Examples: voice input, repo write, markdown generation, scheduled automation

## File Type

A format consumed or produced.
Examples: md, json, yaml, tsx, csv

## Workflow

A reusable multi-step process.
Examples: capture → structure → draft → save

## Task Run

A concrete instance of using the system.

## Artifact

An output or stored object produced by a run.

That’s the ontology.
