## Standard Operating Procedure (SOP)

### SaaS Product Delivery: Milestones & Phases Framework

Document ID: SOP-PROD-DELIVERY-001

Version: 1.0

Owner: Operations

Applies To: All product development activities

Product Context: Multi-tenant SaaS built on

Next.js, Prisma, Neon, Clerk, shadcn/ui

### 1\. Purpose

This SOP defines the standard milestone and phase structure used to plan, execute, and govern SaaS product development.

The objective is to:

Align business, product, design, engineering, and marketing

Establish predictable delivery checkpoints

Ensure auditability, accountability, and scalability

Reduce execution risk and scope ambiguity

This SOP replaces ad hoc sprint-only planning models.

### 2\. Definitions

#### 2.1 Milestone

A Milestone is a business-significant delivery checkpoint representing a validated state of the product.

Milestones are outcome-driven, not activity-driven.

Examples:

“Architecture validated”

“MVP publicly launched”

“Platform hardened for scale”

Milestones are approved by Operations and Product.

#### 2.2 Phase

A Phase is a bounded execution period within a milestone.

Phases are typically aligned to 2-week sprints, but may span multiple sprints.

Phases exist to:

Organize work types

Sequence risk reduction

Structure reviews and handoffs

#### 2.3 Relationship

Milestone = Why we are building Phase = How we progress toward it Sprint = How teams execute day-to-day

### 3\. Canonical Milestone Model (Industry Standard)

This organization adopts a three-milestone SaaS delivery model, consistent with modern product studios, venture-backed SaaS teams, and enterprise internal platforms.

### 4\. Milestone 1: Foundation & Architecture

#### 4.1 Milestone Objective

Establish a validated product direction and technical foundation before committing to full-scale development.

No public users.

No revenue expectations.

Risk reduction is the priority.

#### 4.2 Phase Structure

#### Phase 1.1 – Product Discovery & Definition

Purpose: Validate the problem and define scope.

Primary Owners: Product, Operations

Supporting Teams: Design, Marketing

Key Activities

Market and customer problem synthesis

ICP and persona definition

Pricing and packaging hypotheses

Risk and compliance identification

Success criteria definition

Primary Outputs

Product Requirements Document (PRD)

Initial roadmap

Feature gating assumptions

Business constraints (legal, financial)

#### Phase 1.2 – Platform Scaffolding & Systems Setup

Purpose: Establish technical and operational foundations.

Primary Owners: Engineering, Operations

Supporting Teams: Design

Key Activities

Repository and CI/CD setup

Authentication and tenant model scaffolding

Database schema baseline

Design system alignment

Operational tooling (billing, CRM, accounting)

Primary Outputs

Running development environment

Core system integrations

Design primitives

Operational readiness baseline

#### Phase 1.3 – Internal Alpha Validation

Purpose: Validate system integration end-to-end.

Primary Owners: Engineering

Supporting Teams: Product, Design, Operations

Key Activities

Internal-only deployment

Integration testing

Security posture validation

UX flow validation

Observability baseline setup

Primary Outputs

Internal alpha environment

Known-risk register

Go / No-Go recommendation for MVP build

### 5\. Milestone 2: MVP Build & Launch

#### 5.1 Milestone Objective

Deliver a publicly usable, sellable MVP that validates product-market fit.

Revenue may begin.

User feedback is actively collected.

#### 5.2 Phase Structure

#### Phase 2.1 – Core Feature Implementation

Purpose: Build MVP feature set.

Primary Owners: Engineering, Product

Supporting Teams: Design

Key Activities

Implementation of core workflows

RBAC and billing enforcement

MVP UI completion

Feature flagging

Test coverage for critical paths

Primary Outputs

Feature-complete MVP

Deployment-ready builds

Release notes

#### Phase 2.2 – Quality Assurance & Launch Readiness

Purpose: Reduce launch risk.

Primary Owners: Engineering, Operations

Supporting Teams: Product, Design

Key Activities

Regression testing

Performance and load validation

Billing edge case testing

Accessibility checks

Incident response readiness

Primary Outputs

Launch approval

Rollback plan

Monitoring dashboards

#### Phase 2.3 – Soft Launch & Feedback Loop

Purpose: Validate real-world usage.

Primary Owners: Marketing, Product

Supporting Teams: Operations, Engineering

Key Activities

Controlled public release

User onboarding

Feedback capture via CRM

Usage analytics monitoring

Rapid iteration on blockers

Primary Outputs

User feedback reports

Conversion metrics

MVP validation assessment

### 6\. Milestone 3: Expansion & Hardening

#### 6.1 Milestone Objective

Transition from MVP to a stable, scalable, commercially credible platform.

#### 6.2 Phase Structure

#### Phase 3.1 – Feature Expansion

Purpose: Deliver high-value enhancements.

Primary Owners: Product, Engineering

Supporting Teams: Design

Key Activities

Advanced feature development

Enterprise readiness features

Configuration and admin tooling

Data export and reporting enhancements

Primary Outputs

Expanded feature set

Updated documentation

Upsell-ready capabilities

#### Phase 3.2 – Platform Hardening

Purpose: Improve reliability and security.

Primary Owners: Engineering, Operations

Key Activities

Performance optimization

Security patching

Permission audits

Observability improvements

Cost optimization

Primary Outputs

Hardened platform

Security and performance reports

Reduced operational risk

#### Phase 3.3 – Growth Enablement

Purpose: Support scale and repeatability.

Primary Owners: Marketing, Operations

Supporting Teams: Product

Key Activities

Marketing automation

Sales enablement materials

Customer lifecycle optimization

Retention and expansion strategies

Primary Outputs

Growth campaigns

Refined positioning

Scalable operating model

### 7\. Governance & Review Cadence

| Event | Timing | Participants |
| --- | --- | --- |
| Milestone Kickoff | Start of milestone | Ops, Product, Eng |
| Phase Review | End of each phase | All teams |
| Milestone Review | End of milestone | Leadership |
| Retrospective | Post-milestone | All teams |

### 8\. Compliance

Deviation from this SOP requires:

Written approval from Operations

Documented rationale

Updated risk assessment

### 9\. Conclusion

This SOP reflects how modern SaaS organizations actually deliver software:

Outcome-driven milestones

Risk-reducing phases

Clear ownership

Auditable structure

It is intentionally conservative.

That conservatism is what allows speed later.
