# Architecture Plan

RateLtd should keep the existing TypeScript/Ink harness disciplined while expanding into a full local operator console.

## Architecture Goals

- Keep the CLI boundary thin.
- Keep app composition focused on wiring.
- Keep controller/state responsible for navigation, modal state, command state, target repo state, async jobs, and derived UI state.
- Keep screens compositional.
- Keep reusable components presentational.
- Keep filesystem, process, Git, PowerShell, settings, and logging behavior in typed services/utilities.
- Use discriminated unions for app modes, task states, modal states, command states, workflow states, and result states.
- Use typed result objects for fallible operations.
- Avoid untracked async mutation.
- Preserve Windows and PowerShell friendliness.
- Keep stdout/stderr behavior deliberate.

## State Model

RateLtd should use explicit state contracts for:

- current target repo
- active screen
- selected panel/region
- focused control
- input mode
- modal state
- command state
- workflow state
- clipboard payload state
- session state
- notifications
- settings
- diagnostics
- active editor buffer
- active diff target

## Input Router

Input priority should be explicit:

1. Text-entry mode.
2. Confirm dialog or modal.
3. Screen-local shortcuts.
4. Global navigation shortcuts.
5. Global quit/help shortcuts.

Required behavior:

- Global shortcuts must not fire while typing.
- Modal shortcuts must override screen shortcuts.
- Destructive actions require confirmation.
- Escape/back behavior must be predictable.
- Long-running commands must support cancellation or safe ignore-after-navigation behavior.

## Command Lifecycle

Command state should be explicit:

- idle
- queued
- running
- succeeded
- failed
- canceled
- timed out

Each command should capture:

- command ID
- command label
- command text
- cwd
- started time
- finished time
- duration
- exit code
- stdout
- stderr
- warnings
- risk level
- source screen/workflow
- log reference

## Service Boundaries

### File System Service

Responsible for:

- reading files
- writing files
- deleting files
- creating directories
- moving files
- detecting binary files
- path normalization
- safe root checks
- file metadata
- file watching

### Process Runner

Responsible for:

- child process execution
- PowerShell execution
- shell selection
- stdout/stderr streaming
- cancellation
- timeout
- exit code capture
- ANSI handling

### Git Service

Responsible for:

- git status
- diffs
- staged/unstaged state
- branch info
- commits
- staging
- unstaging
- reverting
- compare operations

### GitHub Service

Responsible for:

- remote detection
- GitHub CLI/API adapter
- auth status
- PR info
- branch status
- CI/check status
- PR creation helpers

### Settings Service

Responsible for:

- reading settings
- writing settings
- validating settings
- migrating settings
- recovering broken settings
- resolving global/local/workspace overrides

### Logging Service

Responsible for:

- events
- sessions
- runs
- command results
- file write logs
- clipboard parse logs
- exports
- retention
- redaction

## Adapter Strategy

External systems should be wrapped behind typed adapters:

- termcn UI adapter
- PowerShell script provider
- Monaco companion adapter
- git-split-diffs adapter
- GitHub CLI/API adapter
- Codex handoff adapter

The RateLtd core remains TypeScript/Ink. External tools become providers, not the architectural center of gravity.

## Type Contracts

Required shared contracts:

- `Result<T>`
- `CommandResult`
- `CommandDescriptor`
- `WorkflowDescriptor`
- `WorkflowStep`
- `WorkspaceResult`
- `FileOperationResult`
- `GitOperationResult`
- `EditorOperationResult`
- `DiagnosticResult`
- `NotificationEvent`
- `LogEvent`
- `SettingsDocument`

## Migration Tasks

- Rename user-facing MeatHarness labels to RateLtd.
- Preserve old config/session compatibility during migration.
- Migrate screen names to RateLtd taxonomy.
- Keep internal IDs stable where possible.
- Add migration bridge for `.meatharness` to `.rateltd`.
- Avoid breaking existing launch/write/ops/output flows during refactor.
